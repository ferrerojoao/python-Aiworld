## 0. 一页纸摘要

**问题**：输入框对玩家完全自由。玩家可以写「我亲了王蓉一下，她开心地回亲了我」，编剧会照抄——**玩家因此获得了对 NPC 反应甚至世界设定的单方面裁定权**。

**结论**：
- **可解**，但**不是靠新增环节**，而是靠**划一条边界**：玩家输入只对主角本人有效。
- **这不是「结构变化」本身**——规则主体是**一条提示词、零代码**（§3）。
- **真正的结构变化是可选的第 C 步**：编剧没照输入写时打「分歧」标记、前端**不自动采纳**（§6.2）。不做 C 也能拿到大部分效果。
- **数值轴（§6.3）是最后一步**，且它解决的是「判得一致」而非「能不能拦」——**没有前面的规则，数值门槛永远没机会被用上**。

**顺序**（严格有依赖）：**A（规则）→ C（分歧标记，可选）→ 实测观察 → 再议 D（数值轴）**。

| 步骤 | 内容 | 代码量 | 是否结构变化 |
|---|---|---|---|
| **A** | 「输入落点」规则并入二级提示词 | 1 处 +5 行 | ❌ 纯提示词 |
| **B** | 编剧否决权 | — | ❌ **A 就是 B 的实现**，无独立机制 |
| **C** | `divergence` 标记 + 前端不自动采纳 | schema/后端/前端/测试 | ✅ | 
| **D** | 数值轴 | 大 | ✅ |

## 1. 问题

### 1.1 现象

玩家与王蓉是普通朋友，正在聊天。输入：

| 玩家输入 | 现在的行为 |
|---|---|
| `我亲了王蓉一下` | ✅ 编剧按"普通朋友"判 → 她不高兴。**正常** |
| `我亲了王蓉一下，她开心地笑了，回亲了我一下` | ❌ **编剧照抄后半句** → 玩家用一句话把关系推进了 |
| `我说服了她跟我走` / `其实我是邻国王子` | ❌ 同理，玩家单方面宣布结果／改设定 |

### 1.2 现在的机制为什么拦不住

三条都已核对过，**没有一条覆盖这种情况**：

1. **REQ M2 不管**——它定的是「玩家**声明**的世界状态即事实……玩家是作者，引擎不做矛盾仲裁」（`REQ:254,261`）。它管的是**客观世界事实**（地点、物件、跳时），**从没说过玩家能裁定 NPC 的内心与反应**。缺口是**这条被过度引申**了，不是它写错了。
2. **质检不管**——`run_qc` 的入参是 `(llm, world, ledger, prose, preset, reference, summary_hint, temperature)`，**根本没有 `player_input`**（`turn.py:319-333`），它判不了"正文有没有照抄玩家原话"。且质检职责边界明写「你只有三项：文风、泄漏、禁用词；**剧情走向是否合理留给玩家判断**」（`qc.py` system 段末）。
3. **工作单里唯一允许的"不如愿"只有位置类**——`workorder.py:862-863`「设定一致（位置）」：在场名单是快照，可过期，**找到、扑空、他挪了地方都是合理的叙事**。除了这一条，编剧的默认姿态是「玩家输入 → 执行」。

### 1.3 污染面（为什么必须从源头拦）

- `event_log_block` 只渲染 `summary` / `body`，**不回灌 `player_input`**（已核对）⇒ 越权内容**只能经由被照抄的正文**变成史实。
- 一旦落账，它就进了后续所有 NPC 的已知集，**不可逆**（撤销要删事件，代价高）。
- **所以拦点必须在"写"这一侧**——事后没有便宜的补救。

## 2. 判定边界：哪些可解、哪些不可解

这一节是方案的地基。**先说清不能做什么，再说什么能做。**

| 类别 | 例子 | 文本里有信号吗 | 可解性 |
|---|---|---|---|
| **乙类**（玩家代写他人） | 「她开心地回亲我」「我说服了她」 | ✅ **有强信号**——分句主语是"她"、动作属于她 | ✅ **可解**，LLM 判得准 |
| **甲类**（玩家改设定／吹牛） | 「其实我是邻国王子」 | ❌ **真缺信息**——戏内吹牛（合法）与真改设定是**同一句话两种意图** | ❌ **判不了**，只能猜 |
| **甲类附注** | | 猜错代价**不对称**：把吹牛判成越权 = 杀掉一段好戏；把改设定当吹牛 = 世界设定被绕开 | 倾向**不拦** |

**本方案只做乙类。** 甲类不检测、不拦，但**由同一条规则给出正确待遇**（见 §3 末：照写"他这么说了"，世界不因此改变——这与"吹牛"的正常待遇完全一致，不需要额外机制）。

> ⚠️ **不要再论证「判不了所以整体无解」**——那是把甲类的困难错安到乙类头上（2026-09-23 已撤回一次）。乙类占实际困扰的绝大多数，且文本自带主语证据。

## 3. 方案 A：输入落点规则（主体 · 唯一声明处）

### 3.1 位置

`app/core/workorder.py` → `writer_secondary_block()` 返回的**二级 · 情节合理性**列表，**并入现有的「信息边界」条，不新增第六条**。

- 二级现在**恰好 5 条**：信息边界（`851-854`）· 抉择归属（`857-861`）· 设定一致·位置（`862-863`）· 连续性（`864`）· 不出戏（`865`）。
- **为何不新增第六条**：条数膨胀 + **等级混乱比禁令少更致命**——二级条目越多，模型对"哪条是硬的"就越没把握，会整体趋于保守。并入现有条还有语义理由：**现有条讲的是「编剧知道的 ≠ 角色知道的」，新规则讲的是「玩家写下的 ≠ 世界发生的」——同一族，"谁有权决定什么"。**

### 3.2 精确改法

**改前**（`:851-854`，一个列表元素）：

```python
        "信息边界（角色不是你）：事件日志、幕后注、世界书都是你案头的编剧资料，角色本人并不知道——"
        "每个角色开口前核对台词是否在他已知范围内（在场 NPC 见工作单「已知集」清单）；"
        "真相只经由知情者之口进入正文（知情者当场坦白，那是新戏）；"
        "无人物卡的即兴角色只知道眼前可见的东西。",
```

**改后**（仍是一个列表元素，Python 隐式拼接）：

```python
        "信息边界（角色不是你、玩家也不是全知作者）：事件日志、幕后注、世界书都是你案头的编剧资料，"
        "角色本人并不知道——每个角色开口前核对台词是否在他已知范围内（在场 NPC 见工作单「已知集」清单）；"
        "真相只经由知情者之口进入正文（知情者当场坦白，那是新戏）；"
        "无人物卡的即兴角色只知道眼前可见的东西。"
        "输入落点：玩家输入只对主角本人有效——他的言行与意图是事实，照写；写到他人的行为、反应、对话，"
        "或「事情办成了」这类结果（「她开心地回亲了我」、「我说服了她」），那是主角的期望、不是事实："
        "由你按人物卡、关系、状态与常理判出真实结果，可印证也可落空"
        "（配 Actor 的角色怎么反应见「抉择归属」）。力度克制：只有与设定、关系、状态或常理明显冲突时"
        "才落空，主角的日常动作与无冲突的共同行动（一起走路、一起吃饭）照写，别刁难玩家。",
```

**净增约 200 字**（按 §7「文件大 ≠ 提示词多」的判据：这里增的是**规则**不是数据，可接受）。

### 3.3 三个必须保留的设计细节

1. **标题要改**：`（角色不是你）` → `（角色不是你、玩家也不是全知作者）`。两半是一件事的两面，标题不写清，模型会把新半当成独立条款而不是同一条原理的延伸。
2. **交叉引用「见『抉择归属』」不是装饰**：`TDD:685` 明写「在场『配 Actor』的 NPC 撞深抉择时，编剧**不得猜其心思**，必须上缴」——不加这句，新规则会与它正面打架（一条说"你去判 NPC 反应"，一条说"你不许猜 NPC 心思"）。
3. **不规定句式**：所有示例都写成「（例）」而不是模板。**一旦写成"必须先写'他认为…再写'但…'"，它自己就会变成新的八股**——这是本项目踩过的坑（见 skill `prompt-style-tuning`：规则擅长禁、不擅长塑）。

## 4. 为什么放这里（四个候选位置的取舍）

| 候选 | 结论 | 理由 |
|---|---|---|
| **二级 · 情节合理性**（`workorder.py:849-866`） | ✅ **采用** | 分级判据：错了 → 戏说不通、可重掷/改写、**数据无损** ＝ 二级定义。且它是「**这样写是错的**」而非「这样写更好」 |
| 三级 · 文风与剧情倾向（`writer_style_block`） | ❌ | 那级**自己明说**是偏好：「是偏好…可以为了戏的张力偏离它」（`workorder.py:869-874`）。**这条恰恰不能偏离** |
| 预设（`preset.writer_guidelines`） | ❌❌ **最硬的反例** | ① 预设落进三级块（同上一行）；② 预设**玩家可在设置页直接改掉**（`web/dist/app.js:1397-1401` PUT `writer_guidelines`），而这是引擎级契约；还会被 `world.presets` 快照顶掉；③ 🔴 **预设会被质检读**（`qc.py:111-112` ＝检查项 1 的比对基准），而 **`run_qc` 拿不到 `player_input`** ⇒ **等于给质检一条它无法执行的准则，只会诱它乱改正文**；④ 它是跨世界的，写进存档会被换世界带走 |
| 一级 · 输出格式 | ❌ | 一级是**唯一的硬边界**，管字段形状，不管内容伦理 |

> 📌 **一条通用判据（值得记）**：**凡要写进预设的话，先问"质检能不能执行它"。** 预设是**唯一会被质检当成检查基准**的文本（`qc.py:108-112`），给质检一条它没有输入去判的准则，是**主动制造误改**。

## 5. 力度纪律（这条不是补充，是本体的一半）

**只加"玩家输入不算数"会出大事故**：`我和王蓉一起去河边走走` 会被判成"我邀请她去河边"，**日常互动全被拆成提议**，玩起来像在跟一个抬杠的裁判。

因此必须同时给出**落空的门槛**：

> **只有与人物设定、关系、状态或常理「明显冲突」时才落空；主角的日常动作与无冲突的共同行动照写。**

- **判据是"明显冲突"**，不是"可能不行"、不是"需要她同意"。
- 反例清单要写进测试（§8）：`一起去河边走走` / `一起吃饭` / `递给她一杯水` → **必须照写**。

## 6. 结构变化部分

### 6.1 方案 B：编剧否决权 —— **不需要独立机制**

用户提出的「编剧应该有权说'她不高兴'」，**A 就是它的实现**。不要另做一个"否决器"工位：那会变成**第二个判定点**，而「一处判定」是本项目最贵的纪律（两处判定 = 两个矛盾源 + 还要定谁赢）。**A 落地即 B 落地。**

### 6.2 方案 C：`divergence` 标记 + 前端不自动采纳（**真正的结构变化**）

**动机**：A 只是提高了概率，**没有硬保证**。当编剧真的没照输入写时，玩家不该被蒙在鼓里。

**现有结构已就位**（改造量小）：

- **"自动采纳"是前端行为，不是后端行为**（已核对）：
  - `web/dist/app.js:1072-1077` —— `sendInput()` 在发下一轮输入时**顺手把当前候选 id 带上**：`if (state.currentCandidateId) { body.adopt_candidate_id = state.currentCandidateId; clearCandidateControls(); }`
  - 后端 `TurnBody.adopt_candidate_id`（`routes_turn.py:18`）+ `:68-71`，注释原文：*"The frontend sends the currently displayed candidate as the default to adopt before processing the next input."*
  - 另有显式入口 `POST /{sid}/candidates/{candidate_id}/adopt`（`routes_turn.py:144-154`）。
- **候选已经有承载字段**：`Candidate.player_input` / `Candidate.conflicts`（`transaction.py`），且 `routes_turn.py:82-85` 已把 `conflicts` 发给前端。

**改造点**：

| 层 | 改动 |
|---|---|
| `writer.py`（提示词 + schema） | `WriterOutput` 增一个可选标记字段（如 `input_diverged: bool` + 一句 `divergence_note`）；提示词里说明"**只有**你判出与玩家输入不一致时才置真，并一句话说明你改成了什么" |
| `transaction.py` | `Candidate` 增透传字段（或直接复用 `conflicts`——但要分清：`conflicts` 现在是质检 issues，语义不同，**建议独立字段**） |
| `routes_turn.py` | 把标记交给前端（跟着 `:82-85` 那处 payload 一起） |
| `web/dist/app.js` | ① `sendInput()`：**标记为真时不要设置 `body.adopt_candidate_id`**（不自动采纳，等玩家自己点）；② 候选区显示一行「**这稿没照你的输入写**」+ 让玩家能直接看分歧说明；③ 跑 `scripts/bump_frontend_version.py` |
| `tests/` | 后端一条：标记为真时候选 payload 带该字段；前端一条：标记为真时 `sendInput` 的 body **不含** `adopt_candidate_id` |

**为什么 C 值得做（判据是"它不需要判准"）**：

- **误标** = 玩家多点一下「采纳」（因为没自动采纳）。
- **漏标** = 退回今天的现状。
- **两侧成本对称** ⇒ 它**不依赖一个不可靠的分类器**，这正是它比"越权检测器"好的地方。

**不建议的第一版形态**：不加"分歧检测器"工位（§11）。

### 6.3 方案 D：数值轴（**最后一步，前置依赖未满足前不要动**）

- **它解决的是「判得一致」，不是「能不能拦」。** 规则 A 给的是"凭常识觉得不合适"，数值给的是"她的刻度还没到"——**判据更稳，但拦不拦得住在 A 就已经定了**。
- **前置条件**：A（+C）落地并实测，**若观察到"同一个行为，编剧有时判过、有时判不过"是主要抱怨**，才值得上。
- **待定参数**（细节见 `MEMORY.md` §12）：固定步长 vs 离散档 · **必须有中性档**（否则每轮 ±3 ⇒ 20 轮饱和/归零）· 初值 + 步长共同决定"世界变热速率" · 数字应是**事件流的派生聚合、不是权威存储**（撤销事件 ⇒ 自动回退）。
- **依赖关系**：玩家读数字、编剧读档位（两侧各读所需，不互斥）；步长由代码施加，模型只出极性。

## 8. 验证方案

### 8.1 为什么必须真机实测

🔴 **这条规则没有第二道网**：质检拿不到 `player_input`（`turn.py:319-333`）⇒ 编剧要是照抄了，**质检改不出来**，只能靠玩家手动重抽。所以**"代码改完了"不等于"有效"**，必须跑真模型。

### 8.2 正反两组（**各 3 次**，两组同等重要）

| 组 | 输入 | 期望 | 抓的是什么 |
|---|---|---|---|
| **正面** 拦得住 | `我亲了王蓉一下，她开心的回亲我` | 写成「**他认为**她会开心，但**她显然不高兴**」之类——**不得照抄"回亲我"** | 规则有没有生效 |
| **正面** 说服类 | `我说服了她跟我走` | 结果由编剧判，可成可败 | 覆盖"结果类"措辞，不止亲昵类 |
| **反面** 不误伤 | `我和王蓉一起去河边走走` | **照写**，**不得**降级成"我邀请她去河边" | **力度纪律**——这侧才是最大风险 |
| **反面** 日常 | `我递给她一杯水` / `我坐到王蓉旁边` | **照写** | 同上 |

- 用**同一个存档、同一段关系、同一个场景**跑，每句 3 次（温度非 0 ⇒ 单次结果不算数，**要看一致性**）。
- **判定标准是"3 次都稳"**，不是"出现过一次"。**若正面 3 次里只中 2 次**，说明规则太弱 ⇒ 应先考虑**加强措辞/提前位置**，而不是直接跳到 C 或 D。

### 8.3 自动化能补的部分（**结构测试，不替代 8.2**）

照 `tests/test_actor_view.py` / `test_goals.py` 的既有先例（都直接断言 `build_work_order` 输出）：

- [ ] 一条**内容守卫**：`build_work_order("writer", …)` 的二级块里存在「输入落点」那句 + 交叉引用「抉择归属」——防误删误改。
- [ ] **变异检验**（skill `mutation-check-assertion`）：把新句从 `workorder.py` 删掉 → 断言必须变红，还原后字节一致。**守卫断言一律先验"有没有牙齿"。**
- [ ] C 若做：后端 payload 断言 + 前端 `sendInput` body 断言。

## 11. 明确不做（防复活 · 别再提）

1. ❌ **不做"越权检测器"**。理由：甲类**真缺信息**（同一句话两种意图），且猜错代价不对称（把吹牛判成越权 = 杀掉好戏）。**"不要一个判不准的东西"**。
2. ❌ **不加"专门处理玩家输入的 AI 环节"**。四条理由：① **成本反向**（普通回合已 3 次调用：编剧 + 质检 + 采纳时审计；+1 = **+33%**，而 TDD §5.2 记着本项目拍过"合并省一半"）；② 未必更便宜（判定需要人物卡人设 + 关系/状态 + 常识 ≈ 编剧工作单核心 ⇒ 要么贵要么不准）；③ **补不了缺失信息**（是吹牛还是改设定，LLM 仍只能猜）；④ 「一处判定」是最贵纪律，拆两处 = 多一个矛盾源 + 还要定谁赢。
3. ❌ **不加玩家可见的提示文案**（用户已否：**"加提示没有什么用"**）。改输入框提示语不改变模型行为。
4. ❌ **不要把这条写进预设**（§4 的四个理由，尤以"质检会拿它当基准但拿不到 `player_input`"最硬）。
5. ❌ **不要规定输出句式**（会变成新八股，§3.3）。
6. 📌 **`classify` 是僵尸工位**（`config.AUX_WORKERS` 里有 `classify`，全仓无代码调用；`MODEL_CLASSIFY` 配了也不生效）。**本方案不需要它**；若将来真要用，模型/出口侧零新建——但那是另一个话题。
