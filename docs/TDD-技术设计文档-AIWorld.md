## 0. 技术决策摘要

| 决策点 | 选择 | 理由 |
|---|---|---|
| 后端 | **Python 3.11+ / FastAPI** | async 原生、Pydantic v2 做全部 schema 校验与强制输出 |
| 前端 | 原生 JS/CSS/HTML（`web/dist/`，**无框架、无构建步骤**） | 页面量小（正文流/面板/导演窗口/日志）；避免框架与打包负担。代价是静态资源要走 `?v=NN` 手动跳版本号防缓存 |
| 通信 | REST（CRUD/操作）+ SSE（回合交付流） | 单向流用 SSE 比 WebSocket 简单；正文以"整段交付 + 前端打字机"实现（见 §5.5） |
| LLM 接口 | OpenAI 兼容 SDK（base_url 可配） | DeepSeek / Qwen / Ollama / 任意网关通用 |
| 存储 | `events.jsonl` 追加 + `save.json` 原子写 | 正文史实不可变 → 追加式；单机单玩家；文件可读可 diff；崩溃安全 |
| 并发模型 | 单进程 asyncio，回合驱动，无后台世界协程；同一存档同一时刻只处理一个回合/事务 | 世界只在玩家回合内推进；审计为采纳时同一请求内的提交后结算，不做独立后台写协程，天然避免写并发 |
| 事务 | 回合 = 事务：候选区可并存多份候选版本 → 显式采纳指定候选（或唯一候选时下一次输入自动采纳） = 原子提交 / 放弃重掷 = 候选版本增删但不落账 | 玩家是作者；正文与副作用一体成立或不成立，同时不打断连续输入 |
| 提示词装配 | 字符串内联在 `core/workorder.py`（无模板引擎）+ Pydantic（结构化输出） | 工作单是"按账本现算"的动态文档，内联比模板文件更贴近数据源；Jinja2 曾是依赖，现已不用 |
| 世界设定装配 | 两级：世界概要常驻 system（永不裁剪）+ 世界书候选行（id+摘要）随导演工作单、点名才展开全文（标签匹配零 LLM） | 设定常驻不失守；详细条目按需展开省 token、导演不被要求通读 |
| 测试 | pytest + 注入 FakeLLM（录制响应） | 离线可跑、可回归；核心断言=回合事务与信息边界 |
| 包管理 | pip + venv；依赖**只声明在 `pyproject.toml`**（`[dev]` extra 装 pytest / pytest-cov / httpx / ruff） | 单机单项目，够用；`requirements.txt` 已删——双源必然不同步 |

依赖方向（单向）：`api / runtime → workers → core`；`world` 只读内容包；`core` 不 import 任何内容包。

### 2.1 内容包（只读资产，`content/<world>/`）

### 2.1.1 world.json 字段（2026-09-08 / 2026-09-09）

`start_time`（ISO 时间，可选）：该世界的世界钟起点。新建存档与重置存档都回到此时刻；缺省回退引擎默认 `2026-07-14T08:00:00`。`check_world` 校验 ISO 格式。

`~~memory_limit~~`（**2026-09-16 已移除**）：原为 experiences 回溯条数上限。搬到**系统设置**（见 §12「注入上限」）——它是玩家的阅读/成本偏好，不是世界设定；写在 world.json 里意味着换个世界就得重配一遍，而"嫌 NPC 记性太差"是跨世界的诉求。字段、`loader`/`draft` 的读写、世界工作台的编辑入口、以及已无调用方的 `Ledger.experiences()` 全部删除（旧存档里残留的键会被忽略，Pydantic 不设 `extra="forbid"`）。

**键=中文名重构（2026-09-09）**：场景与人物卡的 `id` 即中文名（"校门口"/"朱明"），`name` 字段删除——id 同时是事件 location/participants 成员与 UI 显示名。场景删除 `name`/`open_hours`/`adjacent`/`tags`，新增 `region`（消息域地域词，空=全域公共区）；人物卡删除 `name`/`tags`，新增 `region`（听域列表，空=按亲历推导）。存档 `save.json` 的 `scene_name` 字段同步删除。

`start_scene`（str，可选，2026-09-13）：开局场景（场景中文名）。新建存档与重置存档都落在这里，开场事件也记在这里 —— 主角的第一条位置事实。`check_world` 校验它落在场景表里（空 = 合法，取场景表第一个）。它的引入同时终结了"起始场景硬编码 `main_street`"的历史（qingshi2 等世界根本没有 `main_street` 这个场景）。

### 2.1.2 主角入人物表（2026-09-13 用户拍板）

**决定**：主角不再是 `save.json` 里的独立 `PlayerProfile`，而是 `npcs/*.json` 里 `is_player: true` 的那张卡。**键 = 主角真名**（与人物卡"键即显示名"的全局约定一致）。

**动机（用户原话）**：主角资料和世界是绑定的 —— 主角也是世界的一部分；主角与 NPC 数据结构相同，没有理由分两处放。附带收益：**事件日志直接记人名**，中途换主角也不影响旧日志（旧日志里的名字就是当时那个人的名字，不改写）。

| 之前 | 现在 |
| --- | --- |
| `save.player`（`PlayerProfile`，`id` 固定 `"player"`，真名在 `name`） | `world.npcs[主角名]`（`NpcCard`，`is_player=True`） |
| 事件里写魔法串 `"player"` | 事件里写主角名（如 `"刘星"`） |
| `player_display_name()` 读 `save.player.name` | 读 `world.player_name()`（= 卡键） |
| 目标归属 `subject: "player"` | `subject: ""`（空串哨兵 = 主角；否则为角色中文名） |
| `PlayerProfile` 无 `region`/`has_actor` | 补齐 `region`（听域）与 `has_actor`（主角恒 false） |

**不变量**：
- 人物表有且仅有一张 `is_player` 卡。`load_world` 在缺失时补一张占位卡（名 `主角`），保证 `world.player()` 恒有返回值——引擎处处以主角名为键，缺卡会静默失配。**已开局的档上被补占位卡 = 一次隐式换人**，所以 `GET /sessions/{sid}/world/check` 会额外报一条 problem，且**只报不改**（见 §2.1.4）。
- **主角不可删**：世界工作台的人物卡不给主角卡删除按钮（前端），`save_world_assets` 服务端再校验一次（非 1 张 → `ValueError` → HTTP 400，且校验先于落盘，原文件不受影响）。**开局前**该路径照旧；**开局后**主角锁定闸（409）先于这条不变量闸（见 §2.1.4）。
- **主角不可退场**：导演 `retire` 与审计 `lifecycle` 两条路都显式排除主角（否则一句"她离开了"就能把主角从世界注销）。
- **主角不配 Actor**：`roster`（在场 ∩ 配 Actor）显式排除主角，不依赖"主角卡没勾 Actor"这一约定。
- **不重复渲染**：主角卡在 `character_block`/`private_notes_block` 的"在场 NPC"段被跳过（主角另有 `[主角]` 独立段），`known_set_block` 也不算主角的已知集（主角的知识边界就是事件日志本身）。
- **镜子不给镜子**：主角自己不出现在"在场"列表里——`scene_description` 与 `/state.present` 都剔除主角（那是"还有谁在"）；工作单的在场名单里保留他并标注 `（玩家）`（Actor 要认出对话对象）。**唯一例外是左栏「在场人物」**（2026-09-21 用户要求）：那一栏要回答"我眼前有谁"，所以主角列在**第一行**并挂「主角」标签——由 `/state.player_present`（引擎的位置推导）决定要不要列，判据不在前端另算。`present` / `present_ids` 保持不含主角。
- **改名 = 换人物表键**：走资产写路径 `PUT /sessions/{sid}/world`（改卡键与 `card.id`，两者必须一致）；旧日志保持原名。**开局后改名同锁**（= 换键 = 与换人同一类错位，见 §2.1.4）。

**移动途中的特例**：工作单的 `scene` 可能是本轮才解析出的目的地，主角的位置事实还停在旧场景 —— `scene_snapshot_block` 此时把主角补进名单最前（工作单永远是主角所在场景的工作单）。

### 2.1.3 快速造世界：种子与一句话草稿（2026-09-13）

**动机**：世界随时可写（工作台直编世界目录），所以"造世界"不该是一次性的填表工程，而应该是**给最小种子、剩下的边玩边长**。开局 = 新建一个世界（空白种子或一句话草稿），它同时也是你正在玩的存档。

**最小可玩包的下限**（实测 qingshi2 = 5 场景/3 卡/4 世界书条目，shenshan = 3/3/2，但那是舒适值不是下限）：

| 文件 | 下限 | 说明 |
| --- | --- | --- |
| `world.json` | 必须有 | `name` 可后补；`start_scene` 空 = 取场景表第一个 |
| `scenes.json` | ≥ 1 条 | 缺场景引擎跑不动（事件 location 无处落） |
| `npcs/` | ≥ 1 张（主角卡） | 主角位置由事件流水推导，缺卡首轮在场名单就空 |
| `lorebook.json` | 可空 | 空数组是合法状态 |

**L1 种子**（`app/world/draft.py::blank_world_assets`）：`world.json` + 1 个场景 + 主角卡 + 空世界书。开场白留空时写一句纪实句「`<主角>来到<开局场景>。`」——**它不是占位符**，而是主角在本世界的第一条位置事实（没有它，首轮工作单的在场名单里没有主角）。

**L2 一句话草稿**（`app/workers/drafter.py`）：一句前提 → `WorldDraft`（`name`/`summary`/`opening`/`start_time`/`start_scene`/`player_*`/`scenes`/`npcs`/`lorebook`）→ `draft_to_assets` 转成**与工作台编辑同一种资产形状** → 前端预览。

- **主角不放在 `npcs` 里**：由 `player_name`/`player_*` 单独给，转换时合成 `is_player` 卡——模型不会把主角写成普通 NPC，转换时也顺手保住撞名时的主角卡。
- **越界一律纠回合法态**：空场景表、`start_scene` 不在场景表里、表单值与草稿值冲突 → 转换侧修，所以"模型乱写"只会让包更小，不会让包坏掉。
- **验收闸门在引擎侧**：`validate_assets()` 在**临时目录**里试写一遍再跑 `check_world`；不合格就把问题清单回灌给模型**修正一次**，仍不合格则如实返回问题（不假装通过）。校验不过的包根本不进 `content/`。
- 草稿是**提案**：预览不落盘，玩家改过、点确认才走落盘。

**落盘只有一条路**：种子与草稿都复用 `save_world_assets`（连主角卡唯一性校验），不新增第二条写世界的路径。

### 2.1.4 主角锁定：一开演就不许换主角（2026-09-21）

**动机**：游戏中途换主角必然错位。换主角本质是**把一个人名从引擎所有"以人名为键"的索引里抽走**：

| 索引 / 机制 | 换人之后 |
| --- | --- |
| 事件日志 `participants` / `known_by` | 历史记的是旧名，新主角**没有历史** |
| `last_location` / `present_at`（`queries.py::_index`） | 新主角在引擎眼里"没有位置事实" |
| `entities[名].states[]` | 状态挂在名字上，**不跟着走** |
| 目标 `subject` | 空串是「主角」哨兵 → 历史目标**静默改归新人** |
| `by_participant` 记忆切片 | 新主角失忆，旧主角的既往不再参与装配 |
| QC 参照区（`qc.py`） | 拉的是**当前主角**的 `personal_secrets` / `private_note` → 泄漏基线整体换人 |
| `save.player_scene` | 镜头还指向旧主角的路径 |

**判据**（`Ledger.game_started()`，唯一实现）：账本里存在 `source != "opening"` 的事件。

- 不用"账本非空"：开档与重置都会写一条 `source="opening"` 的开场事件（`write_opening_event`）→ 按非空判会**重置完立刻又被锁**，与"重置世界可以换主角"直接冲突。
- 不用 `save.meta.next_event_id`：那是实现细节（重置归 1），拿它当判据会把合法入口也堵掉。
- 只有事件自己的 `source` 是一手事实。已知取值：`opening` / `turn`（正文、NPC 移动与退场）/ `state`（状态增删）/ `director`（导演覆写与记忆注入）。**除 `opening` 外一律计入**——导演改的也是历史，换了主角一样错位；缺 `source` 的旧事件按"已开始"算（fail-closed）。
- **不新增状态字段**：账本即真相。新字段要迁移、会与账本不同步，还会被"重置时忘了清"咬。

**锁什么 / 放什么**（只有"谁是主角"是身份）：

| 动作 | 未开始 | 已开始 |
| --- | --- | --- |
| `is_player` 勾到另一张卡（换人） | ✔ | ❌ 409 |
| 改主角卡的 `id`（改名 = 换日志键） | ✔ | ❌ 409 |
| 删掉主角卡 | ✔ | ❌ 409 |
| 改主角 外貌/人格/幕后注/自知的隐秘/听域/`has_actor` | ✔ | ✔ **保留** |
| 改非主角卡的 `id` 与一切其它资产 | ✔ | ✔ |
| 重置世界 → 再换 | — | ✔ **唯一正当路径** |

**实现**：

1. `app/ledger/queries.py::Ledger.game_started()` —— 判据唯一实现，`/world` 与前端共用。
2. `PUT /sessions/{sid}/world`：落盘前 `_assert_player_unlocked()` 比对**主角键集合**（`_player_keys`）。
   - 判据是**集合比对**：换人 / 改名 / 删人三种表现一条收口，**不按 case 打补丁**。
   - **键取 `card.id` 而不是外层 dict 键**：`save_world_assets` 按 dict 键命名文件，`load_world` 却按 `card.id` 建键——**落盘重载后生效的是 `card.id`**（前端 `readNpcs` 两者一起改，只有手改请求体才会碰见这种错位）。`WorldContent.player_name()` 用的也是 `card.id`，判据必须与它同源。
   - **顺序在 `check_assets` 之前**：先过不变量校验会抛"人物表必须有且只有一张主角卡——当前 0 张"这种技术话，而玩家需要知道的是"已开始游戏，主角已锁定"。
   - **409 而非 400**：不是"你填错了"，是"这个存档状态不允许"（与 `PUT /worlds/{id}` 那条 410 的语义分区一致）。
3. `GET /sessions/{sid}/world` 透出 `player_locked`；前端据此把**每一张卡**的 `is_player` 框与主角卡的姓名输入框 `disabled`，并把主角卡那行提示按状态分叉（`主角 · 已锁定（本局已开始）——要换主角请先「重置世界」`）。
   - **每张卡都禁，不只禁主角那张**：锁是全局状态（本局已开始），不是某张卡的属性；只禁主角那张的话，点开另一张卡又能勾上，而那正是要防的事。
   - **前端禁用只是礼貌，真闸门是 409**（M14 教训：只拦 UI 等于没拦）。工作台缓存 `state.worldData` 靠 `refreshState()` 作废，且**只在工作台关闭时**作废——开着就作废会让切页重渲染、冲掉未保存的改动。
4. `GET /sessions/{sid}/world/check` 追加一条 problem：**已开局却丢了主角卡**（外部手改磁盘）→ `load_world` 会补占位卡 `主角`，等于一次隐式换人。**只报不改**：不还原、不猜原主、不落盘，只说明唯一出口是「重置世界」。

**边界**：重置世界 → 流水清空 + 重写开场 → 立刻解锁；只产了候选没采纳 → 账本没动 → 仍算未开始（与"一旦落一条"字面一致）；`POST /world/import` 总是另开目录、**不覆盖当前世界**，不是暗门；`GET/PUT /sessions/{sid}/player` 两条前端从未调用的死接口**已删除**（少一条能绕过的路）。

### 2.2 存档 = 账本（`content/<world>/`，世界=存档 1:1）

**单一真相源（2026-09-13 改版，取代旧"设计 C"模板/副本分层）**：一个世界就是一份存档。世界资产（world.json / npcs/ / scenes.json / lorebook.json）与运行态（save.json / events.jsonl / candidates/）**同住 `content/<world>/` 一层目录**——正在玩的状态就是唯一真相，工作台编辑直写这层，即时生效。没有"改了副本、列表不变"的第二真相。备份/还原走文件：**导出资产包** = 纯资产快照（不含运行态），想要初始状态就开局时导一份 zip 自己保存；世界改坏了 → 删掉它 → 导入资产包得到一个初始态新世界。**导出完整备份** = 资产+事件日志一起打包（换机/复盘）。

物理真源四块：**事件流**（events.jsonl）+ **世界设定**（world.json 概要 ⊕ lorebook.json 世界书）+ **实体档案**（npcs/ 人物卡 ⊕ save.json 运行层补丁）+ **元配置**（世界默认 ⊕ 玩家覆盖）。位置 / 在场 / 秘密 / 公共均无独立存储——全由事件流查询得出（§3）。

```
content/<world>/
├── world.json / npcs/ / scenes.json / lorebook.json   # 世界资产（工作台直编）
├── save.json          # 引擎运行态 + 元配置玩家覆盖 + 实体运行层（原子写）
├── events.jsonl       # 事件流（追加写；正文史实不可变）
└── candidates/        # 候选事务暂存（非账本，可断线恢复；采纳/放弃后清理，见 §4）
```

**事件流记录**（每行一条 JSON，`events.jsonl`）：

```jsonc
// 唯一事件类型：narrative —— 玩家采纳后的正文成史实（叙述即公开的默认落点）
// 同时也是位置/在场查询的数据源：位置由 narrative.location 推导，谁在场由 participants 推导。
{ "id": "ev_00042", "kind": "narrative", "at": "2026-07-14T14:32",
  "location": "校门口",
  "participants": ["刘星", "朱明"],        // 戏中在场者 = 私密名单的名单原料，也是位置推导依据
  "known_by": null,                                // null=公开（人人可引）；数组=私密切名单
  "body": "校门口围了一小圈人……",                 // 史实正文：一经落库永不修改
  "source": "turn" }
```

- **一律记中文名**（2026-09-13）：主角也是人，日志里写"刘星"不写"player"。这是"中途换主角不影响旧日志"的前提——旧日志里的名字就是当时那个人的名字，引擎从不改写历史。

- **known_by 是访问控制状态**：正文（body）不可变；`known_by` 是每记录一个可改字段，改判只重设它、不触碰正文（§7）。
- **位置/在场没有独立记录**：`where_is` / `present_at` 直接从统一事件流的 `location + participants` 推导，不维护额外位置表。

### 2.3 角色状态 · 长期事实（REQ 〇章「角色状态」；2026-09-14 设计）

**为什么单列**：`event_log_block` 只给编剧最近若干条、更早压成 60 字摘要（条数由系统设置给，默认最近 10 条、其中 3 条给正文；见 §12）；`active_lore_ids` 每轮采纳时 `rebuild_active_lore` 清空重建（关键词命中才注入，`LORE_ACTIVE_CAP=5`）。两者都留不住"角色此刻是什么"这种**长期事实**。

**两类，判据 = 引擎会不会读它**（**不合并成一个列表**——合并等于让 LLM 去猜"这条要不要影响引擎行为"）：

| 类 | 例 | 存哪 | 谁消费 |
|---|---|---|---|
| 引擎开关（硬） | `retired`（现状唯一；主角除外） | `entities[名].lifecycle` 独立字段 | 规则：`Ledger.present_at` 跳过 |
| 叙事事实（软） | 免疫普通武器 / 独臂 / 病倒 | `entities[名].states[]` | LLM：编剧 / 审计（Actor 按 `public` 过滤） |

```jsonc
"states": [
  { "id": "st_3f2a91c04d7e",                 // 状态 id：移除靠它精确定位（"骨裂"vs"左臂骨裂"按原文匹配必误伤）
    "text": "普通刀剑伤不了他",               // 一行事实，直接进提示词——只写现状，不写成因（见下）
    "since": "2026-07-20T03:10",             // 获得时的世界钟
    "source_event": "ev_00042",              // 哪条正文给的 → 可追溯 / 可撤销；**也是成因的出处**
    "public": true,                          // 这条状态旁人看得见吗 → 决定**别人**的 Actor 拿不拿（本人不过滤）
    "until": "",                             // 可选：到期失效（"病倒三天"）；空 = 永久
    "expired_at": "" }                       // 非空 = 已失效（失效时刻）。注入侧一律过滤，条目留着供查看/撤销（§2.3.2）
]
```

**Actor 侧的两桶（2026-09-15 接）**：`actor_state_block()` 给 Actor 两段——「你此刻的状态」（**自己的全量，不过滤 `public`**：`public` 说的是"旁人看不看得见"，对本人没有意义，不给他就会出现"腿伤在身却健步如飞"这种自相矛盾的动作）与「在场旁人的状态」（**只给 `public=true` 的条目**，这才是这个字段唯一的正经用途；不在场一律不给）。两桶都**不带** `（至 …）` 与 `（秘）`——那是给编剧排布用的（定终点 / 防泄漏），Actor 只要事实本身。旁人的 `public` 条目**先筛再截断**（否则三条秘辛会把第 4 条公开表现挤掉，Actor 反而"看不见"一件明明看得见的事）。`actor_contract` 同步加了"这两段与「你知道的事」同级"一句，否则新块落在契约认可的信息集之外。

**状态只写现状，不写成因（2026-09-15 用户拍板）**：一条状态 + 一个 `public` 布尔**表达不了"成因私密、表现公开"两层**。写成"沐浴龙血，普通刀剑伤不了他"，`public=true` 会把成因一起交给 NPC Actor，`public=false` 又连表现一起藏起来——两头都不对；拆成"私密条 + 公开条"两条则吃两个额度（NPC 上限才 3）、撤销要撤两次、两条之间的关联还是隐式的。所以**让状态只承载表现**（"普通刀剑伤不了他"），成因留在产生它的那条事件里、由 `source_event` 指得着（`source_event` 此前只有测试在读，这条口径把它变成成因的正经出处）。于是 `public` 收窄成干净的一句：**这条状态旁人看不看得见**——可见（`true`）写旁人能观察到的表现（"左腿瘸了"），不可见（`false`，默认）写不外露的事实（"其实色盲"）。落地时**全库无存量数据**（`content/*/save.json` 的 `entities` 为空、事件流里 `source:"state"` 0 条），所以只改提示词口径与文档，**不需要迁移**。

**放 save 而不是人物卡**：世界资产维持"开局固定 + 补卡事务增厚"的原语义，状态是玩出来的运行态。`POST /sessions/{sid}/reset` 本来就清 `entities` → **重置即清零**，不需要新增规则。

**注入三处**（`core/workorder.py`）：

| 函数 | 改动 | 口径 |
|---|---|---|
| `character_block()` | 主角段后加「状态」行（**恒在**）；在场 NPC 同理 | 全知。**状态里只有现状**——成因要从事件日志 / `source_event` 看；不公开条目挂「秘」，供编剧填 actor 的 `context` 时避让（2026-09-15） |
| `build_audit_work_order()` | 新增状态段 | 全知（否则判出与状态自相矛盾的正文）。不带「秘」标记——审计不写 NPC 情境 |
| `build_actor_work_order()` | 新增 `actor_state_block()` | **自己的全量（不过滤 `public`）+ 在场旁人的 `public` 条目**；不在场不给；不带 `（至 …）` / `（秘）`（2026-09-15 接） |

**上限与截断**（`STATE_CAP_PLAYER = 6` / `STATE_CAP_NPC = 3`）：角色状态是**常驻**注入，每加一行都是永久预算成本。截断按**录入顺序**（重要的往上放），与 `rules.lorebook` 归属条目的口径一致——不按时间排，因为重要的状态未必是最新的（"天生盲眼"比"今天擦伤膝盖"重要得多）。只吐 `text`（+ `until` 的到期日提示）；`source_event` / `public` 是给机器看的，不进提示词。**被截断必须显式说明**（"另有 N 条状态未列出"）——静默消失会让玩家以为状态丢了。

**门槛：什么才算状态（2026-09-14 用户反馈后收紧）**：本条的门是**提示词纪律**，不是机械守卫——中文语义判据做不成硬闸（"额角缠着纱布（前几天打架留的）"里就含事件信息，但它确实是状态；正则拦这类必然误伤）。纪律的核心是一句自检问句 + 三条反例：

- **自检问句**：*过几天、几十轮回头看，这条还成立吗？* 这一场戏结束就没了 → 别写。
- **不算状态的**：① **消息 / 情报 / 听说的别人的事**（"听说她妈住院了"）——那是**事件**，② 经历已经承载，且写进了编剧视野；要长期追踪这条线请走 **M14 剧情目标**，不要塞进状态；② **一次性的当下**（心情不好 / 手上沾了泥 / 手里拿着棍子）——随时会变，不是"他是什么"；③ **某个角色自己的隐秘与前史**（"他爸欠了债"）——那是 ① 人物卡的事。
- **配套**：`until` 由审计给（"病倒三天" → 具体日期），落地时校验可解析（`_clean_until`，收不下当没给——存进去的后果是**永不到期**，比不给更糟）；说不出"这能量到一个日子以后"，多半本来就不该是状态。**拿不准 → 空数组**：状态常驻后面每一轮的提示词，宁缺勿滥。

**写入与落地（Step 2a，2026-09-14）**：`Transaction.commit()` 在时间结算之后调用 `_apply_state_changes(candidate, audit_out, clock)`，顺序 **① 到期清算（规则）→ ② 新增 → ③ 移除**：

- **到期清算**（`_expire_states`）：`until` 已过的条目**标记失效，不删条目**（2026-09-14 晚改，见 §2.3.2）——写 `expired_at` + 落一条记账事件，注入侧按它过滤。`until` 解析失败**一律当永不到期**（宁可不清理，不要误删）。`expired_at` 同时兼作"已记账"哨兵，否则每轮都会重新越过 `until`、每轮再写一条"状态结束"。
- **新增**（审计 `state_add`）：守卫只管**格式与归属**——`npc_id` 必须在人物表、`text` 非空、同角色去重（否则审计每打一架就把"他刀枪不入"再报一遍，格子很快被同一事实吃光）、**同角色本回合最多 1 条**（防"给同一个人一口气编一串"）。**全局不设硬顶**：三角色同场各自变化是合理的。语义上的过度发挥由提示词纪律（"只从正文读到"）与玩家事后撤销兜底。
- **移除**（审计 `state_remove`）：审计**看着带 `[st_xxx]` 的清单**按 id 报，找得到才删（找不到 → `skipped`，不误删近义条目）。**已失效的条目跳过**（`expired_at` 非空 → `skipped: "已到期（到期清算已处理）"`）：① 已经宣布它结束过，再 pop 一次会**重复落一条「状态结束」**，还会把条目从存档抹掉——而「失效不删除」正是留给玩家撤销入口的（2026-09-15 补守卫；审计读不到失效条目，故撞车只可能发生在同一回合内）。
- **审计失败（`audit_out is None`）→ 状态一动不动**（不能因为审计炸了就丢玩家的状态），但到期清算仍照跑（那是规则，不依赖审计）。
- 每条落地**强制同时落一条记账事件**（`_append_state_event`）：`body:""` / `location:None` / `source:"state"` / `known_by={本人, 主角}` / `summary="X获得状态：…"`。**"谁看见了这个表现"由正文那场戏承担**——与"导演静默覆写只描述位置、不承载情节"同一条纪律。`source_event` 指向它 → 可追溯 / 可撤销。整批结果留痕在 `save.last_state_change`（长期事实误加的代价高，必须查得出原因），前端事件日志按 `summary` 直接可见（`formatEventSummary` 优先取 `summary`）。

#### 2.3.1 展现与撤销（Step 2b，2026-09-14）

**两个视图，分工按"时效 vs 查询"分**（不是同一份数据的两个入口）：

| 视图 | 位置 | 数据 | 回答的问题 |
|---|---|---|---|
| **本回合变化** | 左侧栏第四分区（无变化则整块不出现） | `last_state_change`（每回合重写 → 天然"只显示最近一次"） | 这次采纳**动了什么**（刚看到编剧给谁安了状态，此刻最能判断对不对） |
| **状态面板** | 顶栏「状态 N」徽章 → 抽屉「状态」页 | `state_view` | 此刻**谁是什么**（查询性需求，按需点开、不占常驻面积） |

- **徽章数字口径 = 编剧这一轮实际读到的条数**（只算主角与在场者、且只算上限内的）。不在场者的状态、被截断的，编剧都读不到，计进去就是在骗玩家。
- **`state_view` 由引擎侧生成**（`workorder.state_view()`，内部复用注入提示词的那套过滤 + 同一组 cap），面板据此渲染 → **面板上"编剧能看到哪几条"与提示词字面同源**，前端不自己算 cap，不会漂移。返回按 **主角 → 在场 → 不在场 → 已退场** 定序（排序规则只有一处），每条分 `visible` / `hidden` / `expired` 三个桶。**一条状态都没有的角色不返回**（2026-09-16 用户要求，主角与在场者也不例外）——唯一例外是"只剩失效条目"的人：面板是唯一的撤销入口，漏掉他等于那条永远清不掉。
- **灰显只有一种含义：编剧这一轮读不到这条**。四个来源统一归它——超出注入上限（`hidden` 单独给**条目本身**，不只是条数，玩家据此清理并腾格子）、不在场、已退场、已到期（`expired` 桶）。组头再挂标签说明是哪种（"不在场 · 编剧看不到" / "已退场"），条目自己带「已到期」。**截断只对"会注入的人"（主角 + 在场者）发生**：不在场 / 已退场者压根不注入，对他们做 cap 截断会造出假的"超上限"分层并说出错误的原因（真实原因是"他不在场"）——所以他们一律**全给**，由整组灰 + 组头标签说明。
- **不公开的唯一标签是「秘」（`public=false`）**，**四处同词**（2026-09-16 拍板）：编剧工单的状态行、导演窗口的状态清单（行尾括注，与「至 …」/「已到期」并列）、抽屉状态面板、左侧栏「本回合变化」。语义就是把 `public` 透给玩家——"这条 NPC 看不出来"，省得疑惑 NPC 为什么没反应。早先的"外人看不出"（面板）与"旁人看不出"（`revise_state` 的记账文案）两种说法**已废弃**：同一个概念换一种说法，玩家得重新猜这两个是不是一回事，导演也得再对照一次（记账文案现为 `可见性「公开」→「秘」`）。**左栏能挂的前提是留痕带字段**：`last_state_change` 的五个桶（`added` / `removed` / `expired` / `revoked` / `revised`）每条都带 `public`——左栏读的就是这份数据，而"已结束 / 已撤销 / 已到期"的那几条在 `state_view` 里已经查不到（撤掉的从存档里没了、到期与移除的另进桶）。前端判据是 `public === false`（**不是** `!public`）：老存档没这个字段时是 `undefined`，用 `!` 会把"不知道"误标成"秘"。
- **哪些条目给撤销**：面板里**每一条**都给 `×`（含不在场 / 已退场 / 已到期的）——面板是撤销的唯一入口，不给就等于"这条永远清不掉"。左侧栏「本回合变化」只对**新增**（`added`）给 `×`：已结束 / 已到期 / 已撤销的灰字标注即可，那次改动已经过去了。`skipped`（审计报歪了 / 找不到 id）是内部诊断，不露给玩家。
- **撤销后那一行留在原地变灰「已撤销」，不是消失**：刚点完行就没了，玩家会怀疑自己是不是点错了、撤掉的到底是哪条。

**撤销的语义**（`Transaction.revoke_state()`，接口 `POST /api/sessions/{sid}/states/{state_id}/revoke`）：

1. **删条目 + 落一条对冲记账事件**（`source:"state"`，summary = `X状态撤销：…（玩家撤销）`）——**正文与已有事件一律不动**（史实不可变，改的是"编剧此后认为他是什么"这个运行态），与"访问状态改判"同一条纪律。事件流里因此查得到谁在什么时候撤的。
2. **记 `last_state_change.revoked`**：前端据此把那一行原地标灰（`setdefault` 兜老存档缺键；`last_state_change` 为 `None` 时只落记账事件——那种情况下左侧栏本来就没有"本回合变化"可标灰）。
3. **找不到 → `False` → API 404**，不做静默成功；**重复撤 → 404**（条目已不在，别再落一条重复的"撤销"史实）。
4. **刻意不在审计工单里做"已撤销清单"抑制**（2026-09-14 用户拍板）：撤销是玩家对自己世界的修正，不额外改变审计的判断依据——正文里那场戏还在，审计再读到就再提议一次，玩家可以再撤一次；不为此在每份工单里常驻一行。
5. **粒度 = 逐条**，**永久可撤**（长期事实越久越可能发现是错的）。不做"清空某人全部状态"这类危险批量，也不做"编辑状态文本"（v1 只给撤销）。

**轻确认而非弹窗**：点 `×` 原地变成「确认 / 取消」。撤销是破坏性动作，但它留痕、且状态还能重新获得，一道轻确认就够。

#### 2.3.2 到期语义 + 导演手改（Step 2c，2026-09-14）

**起因（用户实测追问）**："比如伤了这条状态，过了几轮以后，就撤不了了。"——查实不是"过期就禁用撤销"（后端按 id 全局查找、面板对每条都给 `×`，没有任何门禁），而是**条目先没了**。三条路径（探针实测）：

| 路径 | 机制 | 撤销结果 |
|---|---|---|
| **A** 审计给了 `until` | 时钟越过 → 自动清算删条目 | **404**（条目不在） |
| **B** 无 `until` | 条目独立于事件窗口，永不消失 | 正常撤销（左侧栏已空，要走徽章→抽屉） |
| **C** 审计自己报 `state_remove` | 下一轮落地移除 | **404**（条目不在） |

A 尤其像地雷：`until` 是**审计单方面**给的，玩家没有异议渠道。两条缺口因此成立：① **"加"完全没有**（链路是单向的"审计提出 → 玩家撤销"，审计漏报时玩家毫无补救手段）；② A / C 是"条目被动消失，事后无从追溯也无从撤销"。

**改动 1：`until` 到期 = 失效不删除。**
- `StateItem.expired_at`（新字段）：非空 = 已失效。`_expire_states` 只写它 + 落一条记账事件，**不 pop 条目**。它同时兼作"已记账"哨兵——没有这个守卫，每轮都会重新越过 `until`、每轮再写一条"状态结束"。
- 注入侧（`_visible_items`）一律过滤 `expired_at` → 编剧与审计都读不到（"到期"要真的停止影响正文）。
- 面板把失效条目放进 **`expired` 桶**（不进 `visible` / `hidden`——那两桶会说"编剧看得到 / 超上限"，而这条的真实原因是"到期了"），灰显 + 标「已到期」+ **保留撤销入口**。
- 去重改成只比**未失效**的条目（否则一条已到期的"病倒"会永久挡着下一次"病倒"——这是改语义带出来的新假阳性，审计侧与手动侧都改）。
- 存档会攒已失效条目；清理动作 = 玩家在面板上撤掉（不引入批量清空）。

**改动 2：状态增 / 撤 / 改纳入导演窗口动作集。**
- 导演窗口的既有定义就是"改账本"（覆写 / 记忆注入 / 访问改判 / 剧情目标 / 退场），状态是与这些同级的运行态账本 → 归口一致。
- 动作 `state_add`（`{npc_id, text, until?, public?}`）、`state_revoke`（`{state_id}`，退路 `{npc_id, text}` 做**精确文本**匹配——不做模糊匹配，"骨裂"与"左臂骨裂"必须分得开）与 `state_revise`（2026-09-16 加，见下）。
- 路由走 `request.app.state.turn_runner_factory(session)` 拿 runner，调 `Transaction.add_state()` / `revoke_state()` / `revise_state()`——**与抽屉里的 `×` 是同一条路径**：留痕形状、"（玩家设定）/（玩家撤销）/（玩家修订）"文案、`last_state_change` 记账完全一致，不是一个动作两套痕迹。
- **手动加不做语义门槛**（守卫只管格式与归属：`npc_id` 在人物表、`text` 非空、≤ `STATE_TEXT_MAX`、同角色不重复）。审计那套"只收长期事实"是防它自己在正文里过度发挥的；玩家已经拍板的事再拿语义闸拦人很荒谬（"她其实是色盲"看着像前史，但玩家说了算）。
- **`state_revise` = 原地改字段，不换条目**（2026-09-16，`{state_id, 要改的字段}`）：`id` / `since` / `source_event` 三个锚全保留——"他什么时候起就是这样的"不会因为改一个错别字而被重置成现在。"撤销 + 新增"也能换文字，但正是会丢掉这三个锚，所以它值得单独存在。参数语义：**不给这个键 = 这一项不动**（`None` 与"给了值"必须分开——`until` 给空串是"清掉期限"这个合法意图）；因此它**只认 `state_id`**，不做 `{npc_id, text}` 退路：那个退路在这里天然歧义（text 是"要改的那条"还是"改成什么"），猜错就是改错一条事实。三项都没给、或给的值与现值全同 → **不落事件、不写存档**。已失效（`expired_at` 非空）的条目不接受修订——注入侧读不到它，改文字玩家看不到效果，改 `until` 要么立刻又失效、要么等于偷偷复活一条已经记过「状态结束」的史实；要它回来请撤销后重加。
- 修订留痕进 `last_state_change.revised`（`{id, text, old_text, public}`；`public` 是**修订后**的值，2026-09-16 加），前端「本回合变化」据此把那一行显示成「旧 → 新」+「已修订」标签（**仍给撤销入口**——改错了同样要能反悔）；单出一行的情况也覆盖了：改的是几回合前就存在的那条（不在 `added` 里）时若不出行，玩家改完在左侧栏什么都看不到。**不动 `added`/`removed`**：修订不是增删，混进去会让"这回合多了几条状态"的计数失真。
- 手动改动进 `last_state_change.added` / `revoked` / `revised` → 左侧栏「本回合变化」立刻显示、可即时反悔（`last_state_change is None` 时不记，只落记账事件——那种情况左侧栏本来就没有分区可显示）。留痕条目都带 `public`，左栏据它挂「秘」（`revised` 记的是**修订后**的可见性——玩家刚把它改回公开还挂「秘」就是在骗他）。
- **导演工单必须先看得见才能改**：新增 `workorder.director_states_block()`，内部用 `state_view(full=True)`——**全量**（含不在场 / 超上限 / 已到期）、逐条带 `[st_xxx]`。id 与面板**逐字同源**（玩家说"撤掉朱明那条腿伤"，导演填的就是面板上那个 id；两处各算一遍迟早漂移）。行尾括注与编剧工单同词（`秘` / `至 …` / `已到期`，2026-09-16 统一）：缺了「秘」这一项，导演看不到某条是私密的，改 `public` 时只能瞎猜现值。同时导演侧 `character_block(with_states=False)`：那份"贴着名片"的状态行套 cap、只给在场者，与全量清单口径不同，同场出现会打架——状态在导演工单里只从一处出现。

### 2.4 NPC 落卡 · 地点候选：引擎只给候选，玩家拍板（REQ 三章「即兴角色三机制」+「地点候选」；2026-09-19 设计，同日实现落卡窗口 2.0）

**要解决的问题**：`Transaction.commit` 的 `participants` **不校验人物表** → 未落卡的名字进得了事件流；但 `present_at()` 只遍历 `world.npcs` → **进不了下一轮在场名单 = 当场蒸发**。于是 LLM 顺手捏的人物（"酒保说他叫卢克"）无法沉淀：既不是有卡角色，也留不住。而人物卡**不能自动长**（`NpcCard` 的 persona / private_note / personal_secrets 无法占位；卡还挂 `present_at` / `known_set` / `region` / `has_actor`，让 LLM 造人 = 改写关系网 + 开幻觉入口）。所以中间必须有**第三种态**，并且由**玩家**拍板转正。

**三个状态**：

| 状态 | 有名字 | 有键（运行态） | 有卡（资产） |
|---|---|---|---|
| 即兴角色（酒保 / 伙计） | 否 | 否 | 否 |
| **未落卡的确定人物** | **是** | **是** | 否 |
| 有卡角色 | 是 | 不适用（键交还给卡） | 是 |

**边界只有一条**（不按文本特征加规则）：**有名字** + 与玩家**往来累计 ≥ 2 轮**（`UNFILED_KEY_THRESHOLD`，累计不要求连续）→ 授**键**。没名字的人审计侧就不收（`featured` 只收有名字的），因此天然不计数——"没名字就无从落卡"。

**审计侧两处**（`AuditOutput`，`app/workers/schemas.py`）：

- `participants` 口径收紧为 **主角 ∪ 在场的、有名字的角色**：没名字的布景人物（酒保 / 伙计 / 摊主 / 路人）**一律不进名单**，戏份多少都一样。这同时让事件日志的 `在场者：A、B` 干净下来（`_ctx_tag` 读的就是它），且不必动 `last_location` 索引（它本就无过滤、已含全部参与者）。
- 新增 `featured: list[str]`（别名「出场 / 出场者」）：**本轮与玩家实际有往来、且有名字**的角色。与 `participants` 的区别是本质的——**在场是几何位置**（可继承：口径明说"没移动就原样继承"），**出场是"这一轮真的碰上了"**（不可继承，必须由本轮正文产生）。没有这条区分就建不起计数（拿 participants 当计数会得到"永久在场 = 永远满足阈值"，即 2026-09-19 被否掉的"戏份窗口"方案）。
  - ⚠️ 该字段是**宽松裸 list**（与 `state_add` 同风格）：一条歪条目不该让整次审计结算失败（validation 失败 → 时间/位置/目标全落不了地）。具体归一只在落地时做。

**引擎侧**（`Transaction._apply_featured`，在目标/退场结算**之后**跑——退场者不该再被授键）：累计 `save.featured_counts[name]`；达阈值 → 追加进 `save.unfiled`。三个短路：主角自己不算；**已落卡**（`name in world.npcs`，含中途补卡的情况）→ 从两处移除；**已退场**（`entities[name].lifecycle == "retired"`）→ 从两处移除。

**在场域扩张**（`queries.py::present_at`）：域 = `world.npcs ∪ save.unfiled`。这没有引入新机制——`last_location` 索引本就把全部参与者记了进去，只是以前取不出来。

**注入侧**（`workorder.character_block`）：有卡者照旧渲染名片；无卡者落进一个新的「在场临时角色」块（`UNFILED_CARD_CAP = 3`，超出显式写"另有 N 个未列出"），并声明边界：**"有名字但引擎没有他的档案：只按正文已经写出的事实演，不要补前史 / 来历 / 人际 / 动机 / 隐藏设定"**。这条纪律是必需的——编剧顺手给一段来历，那段来历下一轮就成了"事实"，与日后正式落的卡打架。
- 消费者全部优雅跳过无卡者（`world.npcs.get(...)` 检查遍布 `known_set_block` / `private_notes_block` / `active_lore_block` / `roster`），所以域扩张不炸任何一处；`build_actor_work_order` 由 `roster`（`world.npcs.get` 过滤）守着，未落卡者拿不到 Actor 工作单。

**键 vs 卡分层**：**键是运行态**（`save.featured_counts` / `save.unfiled`，`/reset` 清零，与状态同一条纪律），**卡是资产**（`npcs/*.json`，工作台不动）。键不等玩家（引擎自动授），**落卡等玩家**。

**地点候选（`save.locations`，2026-09-19）**：键 = 地点中文名（与场景表同键），值 = `LocationCandidate{status, aliases, first_seen}`。**一个 dict 覆盖三件事**：待落卡队列（UI 筛 `status == "pending"`）· 别名累积 · 静音名单（`dismissed`）。三种情形由 `Ledger.note_location_candidate()` 处理：已注册（`world.scenes` 里有）→ no-op；已在册且 `dismissed` → **只追加别名、不改 status**（× 是玩家的裁决，审计无权翻案）；否则 upsert `pending` + 别名累积。写入点是 `Transaction` 采纳时（原 `register_scene` 调用点），**`Ledger.register_scene` 已删除**——写场景表只剩 `POST .../locations/{name}/file` 一条路。
- **解析域 = 已注册场景 ∪ 候选册**（`_resolve_scene` 纠偏、`rules/movement.py::resolve_destination` 寻路都要）。这不是锦上添花：不做的话玩家还没处理的"老巷旧楼"下一轮会被当成新地点、队列排成同义重复的两条；且"去老巷旧楼"会走不到规则路线 1（确定性寻路），等于把目的地的决定权让给 LLM。场景表优先（已注册的才是唯一真相）。
- 审计提示词（`build_audit_work_order`）同时列出候选册，按状态分成两行「待落卡的地点」「已定为临时的地点」，让审计**沿用同一个中文名**而不是自造变体；`register_scene` 的措辞改为"**建议**落卡（不立刻生效）"。
- ⚠️ 落卡**改变听域语义**：未注册地点 = `ADHOC_REGION` 哨兵（公开事件谁都不风闻）→ 落卡后 `region` 留空 = 全域公共区（**所有人**风闻），且 `_event_region` 查表现算 → **追溯生效**。前端必须写出来（`land-warn`），不能藏。

**API**（`routes_sessions.py`）：

- `GET /sessions/{sid}/unfiled/{name}/evidence` —— 该名字在 `by_participant` 里的最近 8 条事件原文 + 最后目击 + 位置。**只做机械提取，一个字都不生成**。
- `GET /sessions/{sid}/unfiled/{name}/draft` —— **AI 草稿**：模型从**已采纳正文里关于他自己的事件**总结出 外貌 / 人格（`app/workers/landing.py`，走 `model_cheap`）。**三条约束**：① 输入只有他自己的原文事件（不喂世界书 / 别人的卡 / 底牌）② 提示词硬性"只总结已写出的，写不出留空，不许推断 / 润色 / 补前史来历人际动机" ③ 本端点**不写任何状态**，草稿只是给前端预填，落盘与否由玩家拍板。⚠️ 这是 **2026-09-19 的教义变更**（旧口径"只机械提取、拟稿由玩家完成"已作废），防线从"不许生成"换成"证据约束 + 玩家核对 + 草稿视觉可分"。没有证据时**不调 LLM**，直接返回空字段。
- `POST /sessions/{sid}/unfiled/{name}/file` —— 落卡。**走的是资产编辑同一条写路径**：从内存世界拼出资产形状（`_world_assets_payload`）→ 加卡 → `check_assets` 闸门（`ValueError` = 不变量失败 → 400）→ `save_world_assets` → `session.reload_world()`；语义问题随响应带回 `problems`（与 `PUT /sessions/{sid}/world` 同口径：允许半成品态存在，但它必须被看见）。落成后从 `unfiled` 与 `featured_counts` 移除。**不新增第二条写世界的路径**。表单只收 `appearance / persona`（`NpcCardBody` 其余字段留空默认）——幕后注 / 自知的隐秘 / `has_actor` **不进落卡表单**：前者定义上不可从正文推导，后者是运行时档位，三者落卡后到工作台配。
- `POST /sessions/{sid}/unfiled/{name}/discard` —— 放弃（退回即兴角色）。⚠️ **必须同时清零 `featured_counts`**：否则下一轮一出场计数仍 ≥2、立刻重新获键，撤销形同无效（与"同一个结束不能记两次"同源）。
- `GET /sessions/{sid}/locations/{name}/evidence` · `.../draft` · `POST .../file` · `POST .../discard` —— **地点候选**（2026-09-19 新增，与人物侧同构）。此前审计 `register_scene=true` 直接写 `scenes.json`，而描述只能是 `SCENE_PLACEHOLDER`；现在只记候选册，写资产的唯一入口是这里的 `file`（`check_assets` + `save_world_assets`，`Scene.perceivable` 留空 → 占位句）。`/file` 把候选册里攒的别名一并写进 `aliases`；`/discard` 把 `status` 置 `dismissed`（**不是删除**——别名要留给解析域，否则变体名下一轮又被当新地点报一次）。
- `/state` 新增 `unfiled`：`[{name, location, present}]`——`present` 沿用同一份 `present_ids`，`location` 支撑"玩家离开酒馆后他还挂得住"这个全局入口。以及 `unfiled_scenes`：`[{name, aliases}]`（只含 `status == "pending"`——玩家定为临时的那些不再打扰他）。

**前端**（`web/dist/`）：左栏在场名单里给未转正者挂「未转正」标记并可点；其下一行 `待转正 · N` 入口（**N = 人物数 + 场景数**，N>0 才出现）→ 抽屉的「转正」页（**不入「状态」页**：那里有"一条状态都没有的角色一律不返回"的既有规则，未转正者正好一条状态都没有，会被整条过滤掉）。转正页 = **人物 / 场景两段并列**，每段内每条**收起态只有一行**（展开三角 + 名称 + 状态标签 + ×）：
- 展开（`landingBody`）才发请求：先拉 `draft` 预填字段，**预填的字段挂「AI 草稿 · 请核对」标记**（`land-draft-badge`）——草稿必须与作者手写的字段一眼可分，否则事后再也分不清哪句是从正文总结的（这正是旧教义要防的事）。
- 人物两栏（外貌 / 人格）；场景一栏（描述）+ **只读**名称（键）+ 一行听域后果警告。
- 「已写出的事实」入口已于 2026-09-22 **从前台撤掉**（按钮 + 证据盒子都撤，展开时也不再发 `/evidence` 请求）；`renderEvidence()` / `.land-evidence` 那套样式 / 后端 `GET .../evidence` 一律保留，加回只需把按钮贴回 `landingBody`。
- 「确定转正」POST 到的就是上面那两个端点；「×」原地轻确认（`st-confirm`）后 discard。
- **折叠即省调用**：没展开的条目一个 `/draft` 请求都不发（前端用例里有一条专门钉这个）。

**这个中间态为什么必须自洽**：他此刻该被看见（进在场名单、进提示词、挂得住），但引擎不能替他编档案；他要能被操作（补卡），所以需要一个**全局**入口——左栏是"此刻有谁"的地方，全量与操作放抽屉，与项目既有的「左栏 = 此刻 / 抽屉 = 全量」分工一致。

**证否记档**：把落卡入口放**导演窗口**是已被本项目实测证否的路线——M14 目标与状态增删改的唯一入口都曾在那里，而四个世界的 `goals` **全是 0**、`entities` 0/0/0/1。别再赌第二次。

## 3. 账本读写与查询（ledger/）

- **追加写**：`events.jsonl` 只 append；`store.append_event(rec)` 负责 id 分配（`next_event_id`）与落盘。
- **原子写**：`save.json` 写 `*.tmp` + `Path.replace`；读损坏自动回退 `.bak`。
- **启动加载**：全量读入 events.jsonl 建内存索引（几万条 <10ms，无需数据库）：
  - `by_id`；`by_location`（该地点全部事件）；`by_participant`；`by_kind`。
  - 增量维护：回合采纳 append 后同步更新索引。
- **读接口（查询即真相）**：
  - `where_is(entity)` → 该实体最近一条带 `location + participants` 的统一事件（M18）；
  - `present_at(scene)` → 最近事件中地点为该场景的实体集合（在场者 = 查询不是存储）；
  - `visible_to(viewer)` → 可引用事件集 = 世界概要 ∪ 公开条目 ∪ {私密 \| known_by ∋ viewer} ∪ {本场点名展开的世界书条目}（世界书候选行与展开规则见 §6）；
  - `experiences(entity, viewer)` → ② 记忆条目（规则化拼接，§2.2）。
  - `known_set(npc_id, scene_id)` → NPC 已知集（机械知识边界）：亲历（全量 by_participant，不随滑窗）∪ known_by 含己（by_knower，含改判）∪ 听域内公开事件。公开事件按 **NPC 听域**筛选而非当前场景区域：听域 = NPC 卡 `region` 字段（来属地/听域，可多个）；卡上为空时按其亲历事件发生地推导；推导为空 = 保守空集（不听说任何**带地域归属**的公开旧事）。场景表 `region` 字段声明事件发生地归属，**空 = 全域公共区——此类公开事件人人可闻，不受听域约束**（单区域内容包行为不变）。因此听域为空并不等于只知道亲历：亲历、known_by 含己、全域公共事件三路照常，只掐掉地域新闻这一路；**location 查不到场景的一次性布景 = 哨兵 `adhoc`，不进任何听域的风闻通道**（宁可不闻，不错闻；在场者走亲历通道不受影响，亲历 ad-hoc 也不会把听域推导出 adhoc）。用途：本地人听说本区旧事；**出差外地人**活动场景在本地、但听域仍是家乡，本地打架名声对其不可见。听域为空时仍能看到无 region 场景的公开事件（镇上传闻一类）。写手已知集块与 QC 参照区共用此函数（单一事实源）；Actor 切片仍走 `experiences(self)`（口径一致）。

## 4. 回合事务（候选区 / 采纳 / 回滚）

一回合 = 一个事务。正文过质检送达玩家后仍在**候选区**；**玩家采纳（显式或下一次输入自动采纳）那一刻才原子落账**。

```
Candidate（候选快照，落盘到 candidates/；采纳时由 Transaction 落地）
├── 正文 prose（说书人成品或导演采纳的玩家原文）+ 质检修改记录（conflicts）
├── side_effects：narrative.location（规则目的地）
│                 · events · overrides
│                 （**时间不在这里**——时钟由审计在采纳时独家结算，2026-09-16）
└── 关联信息：player_input / writer_directive / trace_id / mode（重掷档位）
```

- **候选区呈现**：SSE 交付 `candidate` 事件（正文 + 副作用摘要 + 质检修改记录），一个回合可陆续产生多份候选版本，全部保留供玩家比较。玩家操作：
  - **采纳指定候选** `POST /candidates/{candidate_id}/adopt` → `transaction.commit(candidate_id)`：把选中的候选正文与副作用一次追加/写入，随后执行提交后结算；成功后清理该回合其余候选文件。回合闭环。
  - **下一次输入自动采纳（仅单候选时）**：`POST /turn` 时若该回合只有一份未决候选，先自动执行 `transaction.commit()` 再进入新回合；若有多份候选，引擎不自动选择，玩家必须先指定采纳哪一份。
  - **重掷 / 抽卡** `POST /turns/{turn_id}/reroll` → 生成一份新的候选版本，**旧版本全部保留**，供玩家比较，账本零写入。
  - **放弃** `POST /turns/{turn_id}/discard` → 清理该回合全部候选版本，账本零写入；这是明确放弃整个回合，不是重掷。
  - **先开导演窗口商量**再回候选区定夺（候选事务驻留内存并持久化 `candidates/` 暂存，断线可续）。
- **崩溃安全**：候选期未 commit = 未落盘 = 未发生；只有 commit 后的追加/原子写可能落盘。
- **采纳后反悔** = 走导演窗口（改判 / 覆写），与候选区重掷分轨。
- **重掷两档**（各自独立过质检并生成一份新候选）：`rephrase` 同一剧本指令重跑编剧；`retarget` 玩家口述不满处、编剧按意见定向改。（早期设计里的 `redirect` 档未实现，已删。）

### 4.1 候选暂存目录（candidates/）

`candidates/` 不是账本，只保存“尚未落账的提案”。每个候选版本一个 JSON 文件，命名 `<turn_id>_<candidate_id>.candidate.json`；同一回合可以有多个候选文件并存，供玩家比较和选择。

文件内容 = `Candidate` 的单版本可恢复快照：

```jsonc
{
  "candidate_id": "cand_0007",
  "turn_id": "turn_0007",
  "trace_id": "tr_abc123",
  "mode": "initial | rephrase | retarget",
  "status": "pending",               // 正常情况下只存在 pending；采纳/放弃后整文件被删
  "player_input": "第二天去学校",     // 剥离 ((...)) 后的玩家输入
  "writer_directive": "",            // 本回合行内导演指令，重掷沿用
  "prose": "候选正文……",
  "side_effects": {
    "narrative": {"location": "校门口", "summary": "第二天早上出门。"},
    "events": [],
    "overrides": []
  },
  // 时间不在 side_effects 里：时钟由审计在采纳时独家结算
  // （旧候选上可能还留着 settle_to / delta_minutes，pydantic 会忽略，不迁移也能读）
  "conflicts": [{ "level": "major", "desc": "…" }],   // 质检 issues + 编排 notes，原始 dict
  "created_at": "…",
  "updated_at": "…"
}
```

> 在场者 / known_by / 时钟 / 场景注册都不在候选里——它们由审计在**采纳那一刻**结算并直接写入账本（见 §8.1 与 REQ M20）。

生命周期：

1. **创建**：每次候选送达或重掷/抽卡时，以“原子写（tmp + replace）”生成一份新候选文件；旧候选文件**不删除、不覆盖**。
2. **采纳**：显式 `adopt(candidate_id)`，或该回合只有一份候选时下一次输入自动采纳；`transaction.commit()` 成功后删除**该回合全部候选文件**（被采纳的和未被采纳的都清理）；commit 失败则全部保留，允许重试。
3. **重掷 / 抽卡**：新增一份候选文件，旧候选全部保留，供玩家比较；账本始终零写入。
4. **放弃**：明确放弃整个回合时，删除该回合全部候选文件，账本零写入；这不是重掷，不会保留任何候选。
5. **启动恢复**：启动时扫描 `candidates/`，按 `turn_id` 分组装载所有 `pending` 候选到内存；前端展示候选列表供比较，玩家可选择采纳其中一份，或继续重掷，或放弃整个回合。未恢复的 pending 不参与任何账本查询。
6. **清理 / TTL**：正常采纳或放弃后即时清理；异常退出遗留的 pending 文件保留，由“恢复未决候选”流程消费；可配置 TTL（如 7 天）清理长期未处理的候选并记日志。
7. **损坏处理**：单个候选文件损坏时视为该候选丢失，不影响同回合其它候选，也不影响 `events.jsonl` / `save.json`；启动时跳过并告警。

**崩溃安全**：候选文件只代表“提案”，不代表史实；没有 commit 就不影响账本。`candidates/` 可以纳入备份，但不是真相源。

### 5.2 Worker 一览

| Worker | 模型档位 | 温度 | 调用 | 输入 | 输出 |
|---|---|---|---|---|---|
| 编剧（导演+说书人合一） | 主模型 | 0.8 | 每回合 1（深抉择时 2） | 工作单（§6，全知） | WriterOutput（正文+副作用+actor_questions） |
| NPC Actor | 主模型/次档 | 0.8 | 深抉择 +1 | 本人隔离工作单 | 决策块 |
| 质检员 | 辅助模型 | 0.2 | 每回合 1 | 初稿 + 受限参照区（§5.6） | {status, prose, issues, summary} |
| 世界审计 | 辅助模型 | 0.2 | 采纳时提交后结算 | 本回合落账事件 + 相关历史 | 结构性结果 |
| 落卡草稿 | 辅助模型 | 0.3 | 点开待落卡条目时 1 | 该主体自己的已采纳正文（最多 8 条） | 外貌/人格 或 场景描述 |

> **档位 = 角色（worker）**：档位不只决定模型名，还决定**出口**（敲主还是辅那套 base_url，§9）。角色名单只有一份：`config.AUX_WORKERS = {qc, audit, classify, landing}`。

> **合并决策（2026-09-05 拍板）**：导演与说书人合并为单一"编剧" agent——决策和文字一次调用完成，成本与延迟约减半。全知信息直接接触文字笔，泄漏防线转移到质检参照区（§5.6），Actor 深抉择仍走物理隔离（两段式）。原"动机层纪律"随之简化：编剧的幕后判断是瞬时中间产物，不设独立字段承载。
>
> **模型数量**：v1 默认只需要 **1~2 个模型**：编剧 / Actor 可共用“主模型”，质检 / 审计 / 落卡草稿可共用“辅助模型”；甚至可以全部指向同一个本地模型（那就连出口也共用一套）。配置里未指定的档位自动回退到默认主模型或默认辅助模型。（原设计的"意图分类 L1"档位从未落地，已从档位表移除。）

### 5.3 编剧（workers/writer.py）

输入 = 玩家原话 + 本回合导演要求（`((...))` 剥离所得，独立消息："必须执行，但不写进正文、不算玩家台词、不进事件日志"）+ rule_bundle + 工作单。一次调用完成**判定 + 成文**（JSON 强制，先脑中排节拍、再直接写正文）：

```jsonc
{ "prose": "正文全文（必填，按叙述预设直接成稿）",
  "summary": "一句话剧情摘要（事件日志用）",
  "actor_questions": [
    { "npc_id": "朱明",
      "question": "被追问打架的事，朱明是含糊带过还是翻脸？",
      "context": "玩家问朱明昨天为什么打架，朱明想起他爸欠债的由头，好面子、心虚" } ]
}
```

- **编剧只写正文（2026-09-07 拍板）**：`WriterOutput` 仅 `prose / summary / actor_questions` 三字段——时间推进、地点、在场者、私密情境等世界副作用**不再由编剧上报**，一律由采纳时的世界审计从正文语义推断（§5.7）。
- **深抉择不替 NPC 决定**：在场"配 Actor"的 NPC 撞深抉择（内心判断 / 涉密反应 / 是否信任）时，编剧**不得猜其心思**——把这一拍写到抉择点为止，在 `actor_questions` 里上缴；引擎派该 NPC 的隔离 Actor 决定后，编剧二次调用以一稿为底稿、按决策改写整场（§5.4）。档位由玩家直接在世界工作台编辑人物卡管理、不经导演窗口（2026-09-05 合并：原"点名强制档"取消，浅反应一律编剧代笔）。
- `actor_questions[].context` 只写该 NPC 本人会知道的情境——禁止写幕后注等只有编剧知道的秘密（防止经 Actor 回流泄漏）。**人称约定（2026-09-11，只约束 context 字段，正文照旧）**：以该 NPC 为「你」、提到玩家一律写**玩家姓名**（主角名经 `player_display_name` 注入条款；名字未设定时退化为「玩家」）；措辞于 2026-09-12 去否定化（"不再写「玩家」、不得在同句混指" → "一句只用一个人称"）。**位置迁入一级（2026-09-13 用户指出）**：二级先于一级，原先把"context 的人称约定"写在二级，读到那行时 context 还没被定义（前向引用）——字段写法贴着字段定义，故随 `actor_questions` 条目结构一起放进「一级 · 输出格式」；二级「抉择归属」只留机制（何时停笔上缴）并以「（字段写法见「一级 · 输出格式」）」指向。规则讲清后引擎**不再改写人称**——旧实现曾把「你/您」机械替换成「玩家」（假设"你 = 玩家"），反而把本来正确的句子改成自相矛盾的（玩家正是对话者本人），是替换动作制造了"写反"。
- **知情总纲「角色不是你」（2026-09-09 收敛，同日去重）**：编剧案头资料（事件日志 / 幕后注 / 世界书）角色本人并不知道；角色开口前须核对话词是否在其自身已知范围内——亲历、来历（人物卡）、被告知（剧情内），**在场 NPC 以工作单「已知集」清单为准（§6）**：清单外的事（含异地旧事）一律不知，公开旧事只能以"听说的"口吻或不提（轰动可作风闻）。派生：幕后注/私密绝不出口（知情者坦白除外）、无卡即兴角色只知眼前。判断依据 = 已知集清单 + 事件日志各行标注的发生地/在场者/时间（**数据做重活，规则讲原理**：机械清单与标注提供证据，规则只讲原理，不 enumerate 特例）。金科玉律级禁令（2026-09-11 已定级为**二级 · 情节合理性**），与"位置是快照"纪律同构（提示词纪律 + 机械清单混合；时间锚等机制兜底默认不做）。**去重**：旧版"总纲 + 已知集条款"两条各自完整陈述异地不知/外乡人语义，提示词重复——合并为总纲内嵌一句清单锚定（条款 8→5，字符 858→767）；深抉择与 context 泄漏两条、元信息与第四面墙两条各并一条，语义零丢失。
- 时间结算走**两档优先级链**（2026-09-16 去规则化，详见 REQ M20）：① 审计 `clock_to`（玩家输入或正文明确给出时刻 → 定到该绝对时刻）→ ② 审计 `delta_minutes`（自估这场戏实际时长）→ ③ 0。**delta 只可能被加一次**——历史根因是把规则 delta 与审计 delta 相加，而审计工单不接收规则意图，会把整段跨度再估一遍（实测"第二天去学校"多算 5.4h）；现在规则侧不再产出任何时间，该风险从结构上消失。判定模型 = "估这场戏的时长"（2026-09-09 改版）：审计以"玩家经历了什么"为准自行估计，不找时间词——文本里说到时间（"明天见""你昨天答应的"）不是经历时间，给 0；原地续聊也给 0。**举例已从提示词删除**（2026-09-16：样例上界会诱导模型把复合活动压成单一类别，如"吃饭+劝酒+同睡"只给 60 分）。保险丝：审计 delta 单回合夹进 `[0, 1440]`（24h，`transaction.py`），负数按 0；`clock_to` 过早则拒。每次结算的完整留痕写 `save.json.last_settlement`。
- **机密纪律**：编剧读幕后注是安全的（全知），但幕后注绝不允许出现在正文里——这是质检参照区比对的反向检查项（§5.6）。

### 5.4 NPC Actor（workers/actor.py）

- 触发：WriterOutput 携带 `actor_questions`。可派 = **在场 ∩ 配 Actor**（2026-09-11 加在场门槛：Actor 工作单按当前场景拼装，缺席者会拿到错位处境；在场名单与编剧工作单的「在场 NPC」同源，正常上缴不会被误拦）；npc_id 填错（「你」/「玩家」/自造 id）经 `_resolve_npc` 机械救回（先例：`transaction._resolve_scene`），救不回 → 丢弃 + warning，不静默。不可派者一律走第二稿由编剧拍板补全（见上），不再出现"无票问题被丢弃 → 稿子悬空"。
- **输入 = 物理隔离工作单**：`build_work_order(viewer="actor_<npc_id>")`（§6 装配器实现）只含世界硬规则、场景可感知区、本人人物卡（含补丁）、`known_set(self)`（与写手/QC 同口径：亲历 ∪ known_by 含己 ∪ 听域内公开；条数上限 2026-09-16 起与写手/QC **同步走系统设置** `KNOWN_SET_LIMIT`，0 = 全部——原先挂 `world.meta.memory_limit`，那是世界设定而这是跨世界的偏好）。**不含**幕后注、其它 NPC 私密、世界书候选、剧情目标、编剧动机。
- **人称不再由引擎改写（2026-09-11 修正）**：旧 `normalize_context` 把「你/您」→「玩家」，前提"你 = 玩家"是错的——编剧按契约以该 NPC 为「你」，替换会把正确句子改坏。改为两侧契约对齐：writer 侧约定 context 人称（§5.3），actor 侧契约给对应读法（「你」= 自己、**「<主角名>」** = 对话对象——名字由 `actor_contract(npc_name, player_name)` 注入，未设定时退化为「玩家」、归属冲突时以「你知道的事」为准）；`clean_context` 只做 `strip()`。用户消息标签由「编剧旁观视角」改为「以你的处境为视角」。
- **在场名单含玩家、剔自己（同日）**：`present_at` 只遍历 NPC 卡，玩家本不在其中；场景快照块无条件把玩家列在最前并标注「（玩家）」，Actor 视图另用 `exclude=[npc_id]` 剔掉自己。主角名为占位符「你」时退化为「玩家」，免得与契约「你 = 你自己」打架。
- **记忆口径统一（同日）**：Actor 切片由 `experiences` 改为 `known_set`——旧口径漏了"听域内公开"第三来源，与 REQ「引用域内的可引知识（公开条目 + known_by 含己）」及听域规则冲突（实测同一 NPC：`experiences` 0 条 / `known_set` 2 条）。记忆块标题「你记得的事」→「你知道的事」，与契约的引用词对齐（现含非亲历的公开事，"知道"比"记得"准）。顺带修 `known_set` 的 `lines[-limit:]`：补 `limit > 0` 守卫（`[-0:]` 会返回全部，与 `experiences` 的 0 = 无记忆口径打架）。
- 输出决策块（回流给编剧二次调用）：

```jsonc
{ "decision": "含糊带过", "action_hint": "不接话，拉你去打街机",
  "tone": "不耐烦里带点心虚" }
```

### 5.6 质检员（workers/qc.py）——必经前置文字关

> **结构**：质检**只有两段消息**（system + user），而且**不读工作单**——`build_work_order` 里**没有 qc 分支**（编剧 / 审计 / Actor 都走它，质检是唯一的例外）。文案全部在 `workers/qc.py`：`run_qc` 拼 system 与 user，`build_qc_reference` 拼参照区。

- **输入两区**：① 正文初稿（可改）；② **受限知识参照区（只读）**（`build_qc_reference`）——实际拼的是三样：**当前场景的可感知区**（`scene.perceivable`）+ **主角两条边界**（`personal_secrets` 只有玩家自己知道、`private_note` 连玩家也不知道）+ **每个出场角色的已知集摘要**（`ledger.known_set(id, scene, known_limit)`，条数与编剧侧**同一份**，否则会出现"编剧写了、QC 却以为泄漏"的假警报；另附一句"本区域公开旧事该角色均有耳闻、发生在本区域之外的旧事一概不知道"）。参照区与成品分轨——成品只取初稿与改写，参照区永远不进正文。
- **system 段 = 三项检查**（2026-09-10 起编剧准则正文随提示词一起给——此前"按编剧准则核对"却从未给准则文本，文风检查空转）：
  - **① 文风一致性**：按下方给出的编剧准则（`preset.writer_guidelines`，与编剧工作单里的「三级 · 文风与剧情倾向」是**同一块文本**）逐条核对文风 / 描写方式 / 用词，**只动需要改的句子、其余部分原样透传**。准则里列出的每一类问题**都归这一项查**，提示词点名的典型是：**比喻与通感**（修辞连续堆砌、把情绪硬转成"针扎""石子"式体感错位）、**强行转折**（"不是……而是……"、"他没躲"式先抑后扬、为转折而转折）、**不相关对比** → 局部改写为直陈其事。
  - **② 泄漏比对**：某角色台词呈现的知识超出其参照区 → **脱敏改写**（模糊化）。泄漏 = 剧情错误，每个 LLM 都知道它会被查。**秘密禁区**（主角 `personal_secrets` 任何 NPC 说出或提及即泄漏；主角 `private_note` 正文里揭示即泄漏，上限是暗示铺垫）**同归这一项**，靠参照区那两条边界生效。
  - **③ 禁用词**：命中即**局部改写**为等价合规说法（通顺 / 意思不变 / 结构完整），改后记进 `issues`。⚠️ **纯 LLM 改写，没有确定性替换表**——"硬拦"指**必经一次质检调用**，不是正则拦截。
- user 段 = 四个零件按序拼（**非空才给**）：`正文：` → `编剧准则（检查项 1 的比对基准）：` → `参照区（只读，只用于比对）：` → `用户摘要（供一致性比对，必要时在输出 summary 字段给修正版）：`，收尾一句「请给出质检结果。」
- 输出 `QCOutput`（`workers/schemas.py`）= `{ status: "pass|fixed", prose, issues: [{desc}], summary }`；`summary` 仅在**正文被改且摘要语义不一致**（尤其脱敏导致的变化）时给，且只写参照区内的信息（它是事件日志的长期记忆，泄漏会反复出现）。后端两条兜底（`qc.py:124-128`）：**`prose` 为空 → 回填原文**；**`issues` 非空 → `status` 强制 `fixed`**。
- **可跳过（2026-09-08）**：`Settings.qc_enabled`（系统设置面板复选框 / env `QC_ENABLED`，默认开）。关闭后 `run_turn` 与 `reroll` 跳过质检调用，编剧初稿直接进候选——省一次 LLM 调用与等待，代价是文风/泄漏/禁用词无人把关。
- **引擎不做矛盾仲裁（2026-09-05 拍板）**：剧情走向与既定设定的一致性归玩家自决——质检不设矛盾分级、不挂队列、不提示（玩家看不出矛盾说明其不重要）。system 段里也明写了这条职责边界（"你的职责只有上面三项"）。
- **预留增强（2026-09-05 记录）**：① 决策忠实性——Actor 决策块进质检参照，编剧二稿不得违背决策（**仍未做**）；② 秘密禁区——**主角侧已落地**（`qc.py:37-45,95` 把主角 `personal_secrets`「只有玩家自己知道…任何 NPC 说出或提及都算泄漏，必须脱敏」与 `private_note`「连玩家也不知道…只有编剧心里有数」都写进参照区，`tests/test_turn.py` 有断言；此前写成"暂不实施"是文档滞后于实现，勿再据此排期）。⚠️ **NPC 侧未落地**（2026-09-23 核实）：`build_qc_reference` 只读 `world.player()`，**NPC 卡上的 `personal_secrets` / `private_note` 没有进参照区**——编剧作为全知方看得到，质检却拿不到"绝不可进正文"的禁区清单，NPC 自己说漏时这条比对是缺的。
- 质检无幕后注输入（防质检自身泄漏与代答）——秘密禁区原文例外：仅作比对参照，与成品分轨。

### 5.7 世界审计（workers/auditor.py）——采纳时提交后结算

v1 的审计/记账在玩家“采纳”（含下一次输入自动采纳）时，于同一请求内完成，产物进账本影响后续轮。所有账本写入都收敛到采纳这一个串行点，避免后台协程与下一回合并发写 `events.jsonl` / `save.json`。
1. **目标完成判定（M14）**：按已采纳正文判活动目标是否达成（小目标=当事达成；大目标=关键真相/冲突解决；只推进未达成不填）。**层级证据（2026-09-12）**：审计目标块渲染成两级树（`app/core/workorder.py:audit_goals_lines`），大目标行附「其下子目标 x/y 已完成」——**只作参考证据、不是判据**：正文给出明确的关键了结（即使子目标没走完，如玩家绕道达成）即可判完成；只是把子目标推了推、关键冲突没解决就不判。不设"子目标未全完成则禁止判父完成"的硬门锁（避免机械兜底，也避免误伤绕道达成）。
2. **关系结算复核**：M5 关系值结算已于 2026-09-21 取消，此处不再保留接口位（理由见 REQ 〇③）。
3. **生命周期扫描（〇章）**：终态事件（死亡/永久离开）→ 实体置 `retired`（数据全保留；目标留玩家定夺）。**退场留痕（2026-09-12）**：置 retired 的同时落一条轻量事件（summary「X退场（永久离开舞台）」，known_by=[该NPC, 主角名]，source=turn）——事件日志是长期记忆比对基准，静默退场会让"他不在了"无史实可引；已退场者再判不重复留痕。**主角豁免（2026-09-13）**：主角即使被审计写进 `lifecycle` 也直接跳过——主角不可退场。
4. **在场与出场（`participants` / `featured`，2026-09-19）**：`participants` = **主角 ∪ 在场的、有名字的角色**（没名字的布景人物一律不进名单，戏份多少都一样）；`featured` = 本轮**与玩家有往来且有名字**的人。两者是「位置（可继承）」与「这一轮真的碰上了（不可继承）」的区别，也是 NPC 落卡的计数依据（§2.4）。
5. **NPC 离场落账（npc_moves，2026-09-09）**：正文明确写出某 NPC 离开去了别处（回家/回店/告辞离去）→ 审计输出 `{npc_id, location, scene_name}`，commit 追加轻量位置事件（participants=[该NPC]，known_by=[本人+玩家] 去向私密名单制，summary="朱明前往朱明家"）。补上"位置只能被事件改变"的离场半边——离场者不再是主事件参与者，否则快照无法被"离开"更新，出现"已写他回家、名单还顶着刚刚目击"的确定错误。去向未注册也无妨：`present_at` 匹配不上它 = "不在任何已注册场景"的机械表达；没写去向不输出（不猜，宁可不记不错记）；非法 npc_id 静默跳过。

**失败/恢复（2026-09-08 与实现对齐）**：审计在采纳时同步执行；若失败，正文照常落账不回滚，错误记入 `save.json.audit_last_error`（不再静默），当轮副作用不补跑。当前同步模式下每次采纳只跑一次审计，无补跑场景；**若将来改成后台异步**，必须引入 run_id + 幂等补跑 + 写锁/单写者队列。

### 5.8 导演窗口（OOC 旁路，routes_director.py）

仅玩家主动开启，导演纯被动；窗口内一切是戏外话（玩家说了 ≠ 主角说了，导演的话 ≠ 正文）。四类请求：

| 请求 | 实现 | 账本 |
|---|---|---|
| 求建议 | 扫剧情目标 + 当前张力 → 2~3 条建议（收尾型 + 推动型） | 只读 |
| 答疑 | 查账本简略答（档案/事件/目标） | 只读 |
| 剧情讨论 | 多轮磋商 → 产出简略输入建议 → 玩家复制进正文框 | 只读 |
| 幕后事务 | 静默覆写 / 记忆注入 / 事件访问改判（§7）/ 剧情目标 set_goal（设立·废弃） | **玩家确认后落账** |

- 幕后事务与候选区同闸门：玩家提出 → 确认 → 落账。静默覆写 = 写一条统一 narrative 事件（如“朱明在网吧。”，source=director）+ 给该时段排戏，正文以"已发生"为基演。
- **人物卡 / Actor 档位 / 转正 / 场景注册（2026-09-07 改判）**：不再走导演窗口，改由**世界工作台直接编辑**世界目录里的人物卡（单一真相源：人物卡人格/幕后注/自知隐秘、has_actor 勾选、添加人物、添加场景）。导演窗口只保留事件流写操作（覆写/注入记忆/改判）、剧情目标与**角色退场 retire**（2026-09-11：确认后 `entities.lifecycle = "retired"` 不可逆 + 落导演留痕事件 known_by=[该NPC, 主角名]；退场者从 present_at 与主动调度中消失）。**主角例外（2026-09-13）**：主角已是人物表里的一员，`retire` 直接 400 —— 否则一句话就能把主角从世界注销；真正要换主角请改世界工作台的人物卡。
- 观察/打量等描写请求在**正文窗**输入，走正常正文流水线，不进窗口。

## 6. 上下文装配与切片（工作单）

核心函数 `build_work_order(viewer, scope)`——按 viewer 身份现配"本轮工作单"，小且固定：

```
viewer ∈ { writer, npc_<id> }        # 编剧=决策+成文合一（全知）；Actor 走隔离工作单
scope  = 当前场景可感知 ∪ 在场实体 ∪ 对话对象 ∪ 关键历史状态（M8 上下文收敛）
```

| 块 | writer（编剧） | npc_<id>（Actor） |
|---|---|---|
| 世界概要（常驻 system 块） | ✅ | ✅ |
| 世界书 · 候选行（id+摘要） | ✅（按此设定写） | ❌ |
| 世界书 · 点名展开条目正文 | ✅ | ❌ |
| 世界书 · 归属条目（subject = 在场者） | ✅ | ❌ |
| 公开事件条目（现拼记忆条目，含玩家输入） | ✅ | ✅ |
| 私密条目 known_by∋viewer | ✅ | ✅（仅含自己的） |
| 幕后注 / 注入记忆（仅决策者可读） | ✅ | ❌ |
| 剧情目标 / 节奏档 | ✅ | ❌ |
| 本人 persona / 已知集切片（known_set） | ✅ | ✅（与写手/QC 同口径） |
| 场景模板底稿 / 可感知 | ✅ | ✅（可感知原则） |

- **世界书触发机制 v2**（2026-09-07，零 LLM 关键词匹配）：条目 = `{id, keywords, body, always_on}`（无 summary 摘要层）。`save.active_lore_ids` 由引擎两处维护——预结算阶段玩家输入命中关键词追加（上轮事实优先、上限 5 条去重）；采纳阶段清空后按已采纳正文重建。工作单只读该列表，按 id 取条目 **body 全文**（不带 id 前缀，2026-09-10）拼入编剧/导演工作单。**常驻开关（`always_on`，2026-09-10）**：勾选的条目不需要关键词触发，每轮必注入世界书块（渲染带【常驻】标记、排在触发条目之前），不占 5 条触发名额、不吃上限——适配"触发不易保证"的稳定背景（世界规则/长期设定）。世界书无 known_by、天然公开；命中与内容不进记忆流（世界书只读静态，不落账）。
- **世界书触发机制 v3 · 归属通道**（2026-09-13 用户拍板）：条目新增 `subject`（归属角色 = 人物表中文名）。**归属角色在场即注入**（`app/rules/lorebook.py::subject_hit_ids` 对 `ledger.present_at(scene)` 求交），渲染带【归属·角色名】标记、排在【常驻】之后、关键词条目之前；**不占 `LORE_ACTIVE_CAP=5` 的关键词名额**（两条通道各自计数、同一轮按 id 去重）。每人上限 **2 条**（`LORE_SUBJECT_CAP`）：注入侧按录入顺序硬截断（重要的往上放），体检侧 `check_world` 报警告（"超过上限 2（生效只取前 2 条）"），归属角色不在人物表也报警告。**要解决的问题**：NPC 卡只在本人**在场**时才进装配，于是"被别人谈论"时他的深入设定够不着；反过来，本人登场而正文全程只叫他绰号时，关键词又不命中。**定稿口径：一个 NPC 的信息 = 人物卡 + 归属条目才齐全**——卡管"他在场时怎么演"（性格/口吻/在演行为），归属条目管"关于他的事实"（可被他人谈论、也可在他登场时自动带出）；跨界事实一律沉到条目（单点存储、不双写），卡里只留一句关系链指针（如"父亲朱文武"）作为触发桥，不算重复。世界书编辑侧有「归属角色」下拉（满 2 条自动禁用该项），人物卡上显示只读提示"归属世界书条目（在场即注入）"，缺一侧可见可修。
- **Token 预算**（分片可配）：system 块（常驻：世界概要全量 + 角色纪律 + 数值/输出纪律）→ 场景块 → 角色块（在场 persona 精简）→ 记忆块（现拼条目按 viewer 过滤 + budget 截断，超出丢最旧）→ 玩家最近窗。裁剪顺序固定：先砍记忆低相关 → 再压玩家窗——**世界概要永不参与裁剪**（设定常驻，失守即世界观崩坏）。
- **记忆条目拼接模板**（零 LLM）：`{时间} {地点}，{谁} {干了什么}，在场：{…}`。
- **事件日志行标注发生地与在场者**（2026-09-09）：写手事件日志每行附 `（发生地 · 在场者：…）`（id 转中文名，玩家用主角名；发生地取场景表名，一次性场景回退 location_name）——为「角色不是你」知情总纲提供判断依据，含**异地不知**（别处城镇的公开旧事本地角色默认不知，§5.5）。
- **NPC 已知集块（2026-09-09，取代旧"近况块"）**：`known_set_block` 为每个在场 NPC 机械计算知识清单（`Ledger.known_set`，每 NPC 最近若干条（默认 5，见 §12「注入上限」：可调、0 = 全部） + "另知本区公开旧事"兜底句），写手与 QC 参照区共用——**比对基线与写作材料完全一致**。二级「信息边界」配套条款："在场 NPC 的知识以已知集清单为准，清单外的事（含日志中异地事）一律不知"。跨区域效果：新手村英雄事迹对王都 NPC 不可见，玩家自报家门时 NPC 将信将疑；同区域轰动事件自动进听域覆盖本区的 NPC 已知集（风闻免打标）；NPC 听域以人物卡 `region:xxx` 标签为准（缺省按亲历推导，空 = 保守），出差外地人因此听不到本地旧事。
- **规则化拼接的意义**：原料只取已记账字段——每轮概貌稳定、成本确定、不产生正文二次概括的幻觉漂移。

## 7. 秘密与访问控制实现（ledger/access.py）

### 7.1 known_by 落库

- 事件记录落库时，导演在剧本指令中声明私密性（`beat.private` 或 narrative 记录级 `known_by` 初值）：公开情境 → `known_by: null`（默认态，人人可引）；私下情境 → `known_by = 当场在场者`（取该场戏 participants）。不为保密增设字段或场景属性。**审计 private 判定 = 按正文内容（2026-09-09 从情境公式改版）**：判据是"外人会不会知道这事发生过"，不单看地点——私下交底/咬耳朵/无人看见的交易/隐蔽处行事 → true；当众冲突/大庭广众对话/路人可见可闻 → false。
- **participants 判定 = 基线继承 + 明确进出场修正（2026-09-09 改版，与 location 联动）**：玩家**未移动**时，审计以工作单给出的在场名单为默认基线，正文没有明确进出场就原样继承——代词指代（"她笑了"）视为仍在场，指代不清保守保留原名单；摊主/路人等叙事背景不进名单。玩家**移动**时：留在原地的人不进名单（其快照停在原地，防瞬移）；正文里在新场景出现并互动的角色——同行、**被玩家找到**、主动搭话——都计入 participants（亲身参与史实；结尾"他回家了"不影响参与者身份，快照停在目击处）。改动前审计每回合从正文重推名单，正文不点名就丢人（忽隐忽现）且 private 事件的 known_by 随之漏料；移动重置首版漏掉"被找到的人"（实玩抓到：网吧找到朱明聊天却未入参与者名单），当日补齐。机械兜底：commit 时玩家恒并入 participants（`transaction.py`，名单确定性排序）。
- 注入记忆（M16 涉密补全）= 落私密记录 `known_by = [被注入者]`；导演静默覆写写统一 narrative 事件，不额外承载知情语义。
- 装配时的可引用集 = `visible_to(viewer)`——私密名单外的实体查不到这条（§3/§6）。

### 7.2 改判私密 · 玩家纠错（公开 → 私密）——名单直给

正文不动，只重设 `known_by`。**名单由导演/玩家直接给定落账，引擎不做检索起草**（2026-09-09 翻案：改判是补救行为，事件公开期间可能在剧情上传给无数人，逻辑上不可能全部收回——玩家选择改判即接受"已传开者收不回"的逻辑代价，以更大的叙事理由压过它）。落账 = `apply_access_override(event_id, known_by)`，只改访问层；运行期发现个别 NPC 应知情而名单未含，导演补名单或圆场即可（改判粒度单条、可反复修正）。

### 7.3 改判公开 / 官宣

- **改判公开 · 玩家纠错（私密 → 公开）**：清空 `known_by` 恢复公开（不产正文事件、不改旧条目）。
- **官宣不靠改判靠叙述**：导演排一场公开戏落新 narrative（公开情境）→ 全镇可引"他们在一起"；历史私密条目保持私密（翻旧账需逐条点名走上方改判公开）。

技术收益：因为切片是装配时现拼现过滤，known_by 一旦重设，所有 NPC 的记忆切片下一轮自动跟随——**访问状态修正不产生任何缓存失同步**。

**改判必须"看得见"（2026-09-18 修的 bug）**：改判结果存在 `save.access_overrides`（与事件原文分开），而事件日志接口原先直接吐**原始事件字典** → 改判私密之后界面上永远显示【公开】，玩家会以为改判完全没生效（引擎侧其实已经收紧了可见性）。现行契约：`/sessions/{sid}/ledger/events` 与 `/sessions/{sid}/world` 的 `events` 一律走 `Ledger.access_view()`，把有效名单并进 `known_by` 并附 `access_rejudged`（= 当前名单由改判给定；"改回公开"不标）；名录的优先级只在 `Ledger.effective_known_by()` 里写一次，前端不做二次计算。同一条纪律：**可改的字段必须在清单里看得见**。

**事件日志的两条渲染纪律（2026-09-18）**：① **原文名额只发给"有正文"的事件**——状态记账 / `npc_moves` / 退场留痕都是 `body=""` 的 narrative，只走摘要行（否则渲染成空壳行，还把 `event_log_full` 的贵名额从真正文嘴上抢走）；**过滤只在渲染层**，`narratives` 索引本身不动（它同时是 `visible_to` / 已知集第三来源的取数源）。② **事件日志摘要行不带玩家原话**（编剧与导演一致）——`玩家：「…」` 已**整条移除**（`with_player_input` / `input_len` 两个参数一并删除，不留恒 False 的死开关）；本轮输入已作为最后一条 user 消息单独下发，历史各轮的原话再糊进日志既重复又挤占版面。

## 8. 时钟与空间

### 8.1 世界钟（runtime/session.py + runtime/transaction.py）

- 变量：save.json `clock`（datetime），只执行不记账。**起点** = `world.json.start_time`（内容包资产，`world_start_time()` 统一读取；新建存档与重置都回到该值）。
- **推进只发生在采纳那一刻**（`Transaction.commit`），走**两档**优先级链（详见 REQ M20）：
  ① 审计 `clock_to`（玩家输入或正文明确给出时刻 → 定到该绝对时刻）→ ② 审计 `delta_minutes`（自估这场戏实际时长，夹进 `[0, 1440]`）→ ③ 0。
- **时间是审计的独家职责（2026-09-16 去规则化）**：规则侧原有的跳时解析（`parse_time_intent` / `day_start_hour` / `settle_hint` 通道）整条下线，理由见 §5.1。审计 user message 里已带玩家输入，所以"玩家给了具体时间就按玩家要求、没给就自行估计"不需要额外通道；提示词按去否定化写成"时间只向前"。
- 判定依据是**玩家经历了什么**而非文本出现的时间词（"明天见""你昨天答应的"给 0）；纯闲聊 Δt=0；原地续聊给 0。编剧不输出 time_hint。
- **两道机械守卫保留**：`clock_to` 过方向守卫（早于当前时钟 → 拒，防审计把日期填错把时钟拉回过去）；`delta` 走 `max(0, …)` 并夹进 `AUDIT_DELTA_CAP_MINUTES=1440` 保险丝。
- 每次结算的完整留痕（起止时钟 / 依据档位 / 审计估了多少 / 是否被保险丝截断 / 对钟是否被拒）→ `save.json.last_settlement`，`GET /state` 透出给顶栏时钟 hover。老存档里可能还留着 `delta_rule` / `settle_rule` 等键，读取方按缺省处理。
- 离线 = 存档搁置，时钟停留在最后推进时刻，重开从该刻续走。

### 8.2 M17 场景双轨（rules/scenes.py）

- 预置 = 内容包 `scenes.json` 节点（名字/别名/可感知区/region）。别名表在启动时建索引；**邻接图已退役**（2026-09-10，见 §8.5）。
- **现场补建（转正）= 只入候选册，落表等玩家（2026-09-19 改判）**：走进包外地点 → 审计给 `location` + `scene_name` + `register_scene=true` → `Ledger.note_location_candidate()` 记进运行态 `save.locations`（`status=pending`），**不碰世界目录**；玩家在抽屉「转正」页点确定才写 `scenes.json`（`check_assets` + `save_world_assets`，唯一写路径）。一次性布景（`register_scene=false`）只记事件条目的 `location_name` 显示名、不进导航集；玩家点 × = 进 `dismissed` 静音（不再自动入队，别名留着给解析域）。
- **落表内容只有名字 + 玩家确认的描述（2026-09-19）**：别名在候选册里累积，落卡时一并写进 `Scene.aliases`；`perceivable` 由草稿预填、玩家可改，**留空 → 占位 `SCENE_PLACEHOLDER`（"暂无描述。"）**——审计**不代笔**（它的输出字段全是提取式，而"这地方一眼能看到什么"是固有属性，正文没写就得编；编出来的描述看着像设定，进资产后每轮注入编剧与 QC，作者日后分不清哪句是自己写的）。纠偏 `_resolve_scene` 的解析域 = **场景表 ∪ 候选册**（id 优先）。
- 转正信号（引擎被动核对）：玩家回访/指代（指代消解依赖解析域已含候选册）→ 剧情目标指向 → 导演/NPC 复用；任一出现即入候选册（`dismissed` 者只追加别名、**不改 status**——× 是玩家的裁决，审计无权翻案）。导演可预注册（走 `POST .../locations/{name}/file`）。
- 一次性布景：剧情用完即从可导航集退场（事件流仍可回溯）。

### 8.3 M18 位置与在场者（ledger/queries.py）

- "X 此刻在哪" = `where_is(X)`：该实体最近一条带 `location + participants` 的统一事件。
- "谁在当前场景" = `present_at(scene)`：在场 = 查询不是存储。
- **遍历域 = `world.npcs` ∪ `save.unfiled`（2026-09-19）**：域里还要并上**未落卡的确定人物**（有键无卡，§2.4）——他还没有人物卡，但引擎已经认他是「人」，出现在场景里就该被看见。没名字的即兴角色永远不在域里（它们从不进 `participants`，`last_location` 里也就没有它们）。
- **主角与 NPC 同权（2026-09-13）**：`present_at` 遍历 `world.npcs` 全部键，主角在表里 → 自然出现在在场名单里（开场事件即他的第一条位置事实；否则第一轮工作单的在场名单里没有主角）。需要"别把自己算进别人堆里"的地方各自剔除：`scene_description` 与 `/state.present` 剔主角（那是"还有谁在"）；工作单的在场名单保留他并标注 `（玩家）`。**左栏「在场人物」反向取用**（2026-09-21）：它要"我眼前有谁"，于是用 `/state.player_present` 把主角补回第一行并挂「主角」标——同一份 `present_at` 派生结果，两种提问各取所需，谁都不在前端自己算位置。
- **空档位置查询三件套**：过期前最后事件 + 人格隐含大框先验 + 时间差 → 引擎合成候选域 → 导演做叙事落点 → 玩家进门时在场结算对导演落点执行（导演落点本身落一条新事件）。

### 8.4 M1 NPC 位置推断（rules/movement.py）

- 输入：最后事实与覆写（账本）/ 地点标签与开放时段（场景表）。（2026-09-05：正常日程字段已移除）

### 8.5 M19 移动裁决链（rules/movement.py）


- 目的地解析（`resolve_destination`）实际只有两路：① 地点直命中（场景 id / aliases / **候选册别名** 子串表）；② 由人推位置（"找朱明" → M1 最近位置事实）。都未命中 → 返回 `None`，location 与场景**候选**交审计从正文判（未注册的新地点由审计给 `scene_name` + `register_scene=true` → **入候选册，不写资产**，2026-09-19）。

## 9. LLM 网关与模型档位（core/llm.py）

```python
class LLMGateway:                     # 一个实例 = 一个出口（构造时定死 base_url / key）
    async def complete_json(self, messages, schema, *, model, temperature, worker="") -> dict
    async def complete_text(self, messages, *, model, temperature, worker="") -> str

class LLMRouter:                      # 按**角色**把调用分到主 / 辅两个出口（2026-09-20）
    def gateway_for(self, worker) -> LLMGateway     # 懒建 + 按 (base_url, key) 去重
    def resolve(self, worker) -> tuple[str, str]    # (模型名, 出口标签)，装配点与调试卡片共用
    def get_usage(self) -> dict                     # 两个出口**相加**
```

- OpenAI 兼容，`base_url/model/key` 按档位可配；`complete_json` 优先走 JSON schema / structured output，Pydantic 校验 + 显式拒空 `{}` + 失败重试 2 次。
- **两个出口（2026-09-20）**：主模型与辅助模型**各有一套 base_url / api_key**。此前两档共用一个 `AsyncOpenAI`，想"正文用付费 API、辅助用本地 ollama"（或反过来）做不到。
  - **按角色分，不按模型名分**：主辅两侧默认就是同一个模型名（`qwen2.5:7b`），按名字分不出该敲哪个门——"同名模型 + 两个 endpoint"（官方 vs 本地 vLLM）是完全合理的配法。角色是引擎本来就持有的事实，于是它**同时决定模型名与出口**：一处判定、两个结果，不会各自漂。角色名单只有一份（`config.AUX_WORKERS = {qc, audit, classify, landing}`），`resolved_model` 与 `endpoint_for` 都读它。
  - **调用点只报角色**：`worker` 从调用点 → 工位函数（每个工位声明自己的默认角色，如 `run_writer(worker="story")`）→ 网关。`model=` 仍可显式给（测试与个例要钉死模型名时），留空则由角色推。四个实现（`LLMGateway` / `LLMRouter` / `FakeLLM` / `TraceRecorder`）**签名必须一致**——`TraceRecorder` 要原样转发参数，签名不一致就得靠 `hasattr` 嗅探，那种鸭子类型一改就静默失效。
  - **辅侧留空 = 跟随主侧**（`cheap_base_url` 为空即回落，且 base_url 与 api_key **成对**回落）：只填地址不填密钥的用法不存在，分开回落只会造出"新网关 + 旧 key"这种静默生效的半配置。默认态因此仍是单出口，与拆分之前逐字节等价。
  - **网关懒建**：没配辅助出口的部署不会凭空多一个 client / 连接池；两侧填同一套地址则按 `(base_url, api_key)` 去重成**一个**网关，用量只算一遍。
  - **出口必须在日志里看得见**：`TraceRecorder` 的 entry 带 `worker` 与 `endpoint`（形如 `辅 · 127.0.0.1:11434`，**只给主机、绝不含 key**），前端调试卡片 meta 行显示出来。两个接口分开配之后，这是唯一能查出"这一笔到底敲了哪个门"的地方——配错时模型会照常回话，只是回的另一个人。
  - 覆盖情况：**手工实测通过**（用户实测，2026-09-20）；自动化的"路由 + 用量"断言尚未补（当时按用户要求只同步文档）。
- **结构化输出容错（必做）**：当模型不支持 JSON schema、连续失败或返回非法 JSON 时，降级为“提示词要求 JSON + 正则/起止标记抽取”，再交 Pydantic 校验；仍失败则返回用户可见错误，并记录原始响应供排查。禁止把非法 JSON 静默当作空结果。
- `enable_thinking=False` 作为配置项（推理模型默认关思维链省 token）。
- 每调用记结构化日志：`trace_id / turn_id / candidate_id / worker / model / prompt_tokens / completion_tokens / ts`，供成本核查与回合排错。
- **超时与重试必须可预测（2026-09-11）**：三层乘法（`complete_json` 外层 3 次 × SDK 隐形 3 次 × 120s）会让一次失败拖到十几分钟；且 `except Exception` 全捕获会把 404（模型名写错）也白等重试。规则：① `AsyncOpenAI(max_retries=0)` 关掉 SDK 自带重试——重试策略只由网关单点决定，SDK 的隐形重试是不可预测的乘数；② 分级超时 `Timeout(connect=10, read=LLM_TIMEOUT_SECONDS, write=30, pool=10)`，read 取 `AIWORLD_LLM_TIMEOUT_SECONDS`（默认 **90**，2026-09-11 由 120 下调）；③ 错误分流：超时 / 连接失败 / 429 / 5xx → 退避 **1s、2s** 重试；400 / 401 / 403 / 404 / 422 → 立即抛（不可重试，模型原文随异常带出，不再浪费后续尝试）；④ **结构降级优先于 fatal 判定**：`json_object` / `reasoning_effort` 被网关拒绝时回的也是 400，必须先走降级路径，否则会被误判成不可重试而直接放弃；⑤ 本地解析 / Pydantic 校验失败（`extract_json` 与 `ValidationError` 都是 `ValueError`）不算 HTTP 错误，带原文反馈重试；⑥ 外层尝试上限抽为 `_MAX_ATTEMPTS = 3`（未下调）。
  - **实现坑（必须记住）**：openai SDK 内部 HTTP 库是 **httpx2**（独立包，与 httpx 0.28 是两个库）。传普通 `httpx.Timeout(...)` 构造 `AsyncOpenAI` **不报错**、`client.timeout` 也读得出来，但真正发请求时才抛 `TypeError: unhashable type: 'Timeout'`——只有实跑才炸得出来。必须用 SDK 导出的 `openai.Timeout`（实测 `openai.Timeout is httpx2.Timeout == True`）。
  - **调用耗时入 trace（同日）**：`TraceRecorder` 每条 entry 带 `started_at` / `duration_ms`，用 `try/except/else/finally` 保证失败的那一笔也记录（卡住的调用恰恰最需要看耗时）；前端调试卡片 meta 行显示「耗时 1.2s」，≥30s 打黄色「慢」标签（`--warn` 主题变量，明暗两套）。
- 模型档位表（config.py + .env 覆盖）：编剧 / Actor / 质检 / 审计四档，各自 model + temperature（§5.2）；未配置档位回退到默认主模型 / 默认辅助模型，通常 1~2 个模型即可。**出口**（敲哪个 base_url）与模型名分开配：辅侧一套独立地址（见上「两个出口」）。
- **v1 无向量检索**：召回/切片全部结构化查询 + 线性扫（几万条内 <10ms）。二期升级 = 事件流叠语义索引（embedding 落盘、启动重建），对内容包与存档结构零侵入；中文预留 bge 系接口。

### 10.2 SSE（回合交付流）

```
POST /api/sessions/{sid}/turn  {"input": "…"}
  → text/event-stream:
     event: stage        data: {"stage": "writer", "label": "编排成文中"}
     event: candidate    data: {"trace_id", "turn_id", "candidate_id", "prose", "side_effects": {"narrative": {"location": "…"},
                            "events": []}, "conflicts": […]}
     event: error        data: {"trace_id", "message"}
```

> **实时性不变量（P1-5，2026-09-17 补）**：`stage` 必须**在候选算完之前**送达浏览器——前端那段「正在连接…」的阶段提示全靠它，攒到最后一次性发等于没有。这条在 `TestClient` 上**结构性地验不了**（整条流会被缓冲；httpx 的 `ASGITransport` 同理），所以由 `tests/test_sse_realtime.py` 起一个**真 uvicorn**（真 socket + chunked）、用 httpx 逐块读并记录每个事件的到达时刻来守，判据 = 首个 `stage` 到 `candidate` 的时间差 > 0.8s（第一次 LLM 调用被假造延迟 1.5s）。判别力已用变异测试证明：把 `/turn` 改成"先跑完再一次性返回"，三个事件全挤在同一毫秒（差值 0.0006s），断言立刻变红。
>
> 若该回合只有一份未决候选，`POST /turn` 会先自动采纳该候选（等价于显式 `adopt`），再开始处理新输入；若有多份候选，玩家必须先选择采纳哪一份，引擎不自动选择——此时 `POST /turn` 应返回“需要先选择候选”（如 409/提示），或由前端阻止提交直到玩家 adopt / discard。
>
> 候选区操作（普通 POST，非流式）：

```
GET    /api/sessions/{sid}/candidates/pending   # 恢复未决候选列表（断线/重启后用；按 turn 分组）
POST   /api/sessions/{sid}/candidates/{candidate_id}/adopt
POST   /api/sessions/{sid}/turns/{turn_id}/reroll   {"mode": "rephrase|retarget", "note": "…"}
  # 重抽与 /turn 同构：LLM 调用同样套 TraceRecorder 并挂 session.debug_trace（2026-09-11：
  # 此前 reroll 用裸 LLM，调试面板完全看不到重抽过程；2026-09-14 起 /adopt 也走同一个
  # _traced_runner 入口——采纳会触发审计调用，漏包就查不到那笔）
POST   /api/sessions/{sid}/turns/{turn_id}/discard
```

**注入上限（2026-09-16，从世界配置搬到系统设置）**：`event_log_limit` /
`event_log_full` / `known_set_limit` 三个数字**编剧 / 质检 / Actor 三处共用**，
可在 UI「系统设置 → 注入上限」改，落 `data/settings.json`（`SETTINGS_OVERRIDE_FIELDS`
成员，与模型配置同一套覆盖机制）。

- **0 = 给全部**（旧口径"0 = 不给"已废，与玩家直觉相反）。唯一不能为 0 的是
  `event_log_full`——0 条正文等于让编剧无从续写，clamp 到 1。
- **clamp 只在一处收口**：`Settings.limits()` 返回冻结的 `InjectionLimits`
  （负数→0、正文条数→至少 1），UI 与装配层都不各自防御，避免几套口径。
- **装配函数签名不留默认值**：`event_log_block(limit=…, recent_full=…)` 与
  `known_set_block(known_limit=…)`、`Ledger.known_set(…, limit)` 的 limit 都是
  必填（原 `limit=6` 是死参数——所有调用点都显式传值，改它没有任何效果）。
  生产路径由 `TurnRunner` 传 `settings.limits()`；探针/单测可省，退回
  `DEFAULT_LIMITS`。
- 起因（用户实测）："限制太小导致 NPC 总是忘记事，而 token 因为缓存命中，
  消耗没有那么快。" 实测 shenshan（16 条叙事）：默认 10/3/5 → 7631 字符；
  全部/3/全部 → 8457（+11%）；全部/1/全部 → 4856（−36%）。**放开条数很便宜，
  正文原文才是大头**——`event_log_full` 是真正的成本旋钮。
- **原文名额只发给有正文的事件**（2026-09-18 修）：状态记账事件、审计 `npc_moves`
  的移动事件、退场留痕形状都是 `body=""` 的 narrative。它们进 `narratives` 索引是
  对的（亲历 / 召回要走索引），但按位置一刀切当成"最近剧情原文"渲染，只会吐出一行
  空壳 `- 时间（在场者：X）：`，而且把最贵的名额从真正的正文嘴上抢走（实测一轮采纳
  后默认 3 个名额被 2 个空事件占掉）。现在 `event_log_block` 先挑出有正文的事件、
  只给它们发原文名额，其余（含这些记账事件）一律走摘要行——它们本来就有 `summary`，
  信息不丢、名额不占。**过滤只在渲染层**：`narratives` 还是 `visible_to` 与已知集
  第三来源的取数源，索引层不许动。

| LLM 角色说出域外知识 | 视图物理隔离（Actor 输入无导演区）+ 质检泄漏比对（参照区只读）+ 泄漏 = 剧情错误 |
| 本地模型结构化输出不稳定 | JSON schema + 重试 + 文本降级解析 + Pydantic 校验 + 失败给用户可见错误并记录原始输出 |
| 正文与时钟/账本不一致 | 时钟按两档优先级链结算（审计 `clock_to` → 审计 delta → 0），时间由审计独家负责、规则侧不再插手（无跨工位重复计费）；正文与时钟的叙事落差留玩家自决。每次结算留痕在 `save.last_settlement`，顶栏时钟 hover 可查 |
| 时钟被闲聊误推（规则假阳） | 规则刻意克制：无日界词、无相对日界、无 `等到/跳到/直到` 触发词 → 一律不猜，全交审计（假阳比假阴严重，回退机制尚未落地） |
| 时间线分叉（重掷留痕） | 回合事务：副作用与正文同包回滚，commit 前账本零写入 |
| 候选区进程崩溃 | 候选未 commit = 未落盘 = 未发生；`candidates/` 持久化，启动后经 `GET candidates/pending` 恢复多份候选列表；正常操作即时清理 |
| 改判名单不全（已传开者漏收） | 设计口径即接受：改判是补救行为、名单直给，已传开者收不回是玩家明知并接受的逻辑代价；运行期导演可补名单或圆场 |
| 上下文膨胀 | 分片预算 + 模板底稿省 token + 记忆现拼截断 + M8 上下文收敛（装配收敛到当前场景可感知 + 对话对象 + 关键历史状态） |
| 事件流膨胀（远期） | 全内存线性扫可撑几万条；二期 = 语义索引 + compact 预研（对内容包与存档结构零侵入） |
| 审计产物迟到 | v1 采纳时同步结算，无迟到；若未来改异步，必须加写锁/单写者队列，并保留 run_id 幂等补跑 |
| SSE 阶段速报迟到（整条流被缓冲） | 前端「正在连接…」的阶段提示全指望它，攒到最后一次性发等于没有。TestClient 结构上验不了，故 `tests/test_sse_realtime.py` 起真 uvicorn + httpx 逐块读，断言"首个 stage 到 candidate 的时间差 > 0.8s"（变异测试证明：缓冲版差值 0.0006s，必红）。中间件一律用**纯 ASGI**、不用 `BaseHTTPMiddleware`——后者会给流式响应包一层，正是这条不变量最怕的东西 |
| 隐私/安全 | 默认仅绑 `127.0.0.1`。**请求级鉴权已落地**（P1-4，2026-09-17）：`app/api/security.py` 的纯 ASGI 中间件 `TokenAuthMiddleware` 在 `/api/*` 上要求 `Authorization: Bearer <AUTH_TOKEN>`，判定三条 = **只护数据面**（静态面必须裸奔，浏览器取 `<script src>` 带不了头）/ **只护非本机**（回环 + TestClient 放行）/ **失败关闭**（要求鉴权但没配令牌 → 401，不是放行）。用纯 ASGI 而非 `BaseHTTPMiddleware`：后者会给回合 SSE 包一层，有额外缓冲/取消语义风险。启动期 `check_host_security()` 另拦"绑非回环 + 空令牌"。前端用 `?token=` 打开一次即存进 `localStorage`（`authHeaders()` 统一注入，覆盖 `api()` 与 3 处裸 `fetch`）。⚠️ 仍是**明文 HTTP**，只适用于可信局域网；`REQUIRE_AUTH_FOR_NON_LOCAL=false` 可整体关掉（C 方案：绑全网卡 + 防火墙限源网段） |
