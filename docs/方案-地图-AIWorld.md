## 0. 一页纸摘要

**「地图」在本项目里处于一个反直觉的状态**：三个视觉向功能里，场景图 / 人物图**方案齐全**，反而**地图是唯一的空白**——它从来没被设计过，只在需求文档里被**当作一个消费者名字提到过一次**。

**两个卡点**：

1. 🔴 **没有边。** `REQ:211`：**邻接图 / 开放时段已退役**（2026-09-10）——"场景之间没有边，也不再有开放时段字段，'从 A 能不能到 B'不再校验"。**图上没有可画的边。**
2. **没有坐标、没有几何。** 场景节点只有 `id` / `aliases` / `perceivable` / `region`。

**一个意外发现**：`region` **是现存的唯一空间结构，而且内容包早就在当"层级"用**——`sgjz` 包里是「上层 / 下层 / 暗渠 / 集市」。所以**"按分区分组"的形态不需要任何新数据**（§4）。

**建议的形态**（§5，待拍板）：**甲 · 分区地图**（零新数据，＝位置面板加一层分组）· **乙 · 真连通图**（撞退役判据，不建议先做）· **丙 · 地图 = 一张画**（接附图那套，成本最低）。

## 3. 卡点一：边已被退役（`REQ:211`）

> `REQ:211`：「⚠️ **邻接图 / 开放时段已退役**（2026-09-10）：场景之间没有边，也不再有开放时段字段，"从 A 能不能到 B"不再校验。」

**这意味着**：任何"真正的地图"（画连线、算路径、标距离）都需要先**推翻这条退役决定**。

- 那是**复活一个已作废的机制**——本项目对这类改动有一条纪律：**要复活，先立"为什么现在需要它"的判据**（参考数值轴那次：作废时留了三条判据，就是防复提）。
- 而且**寻路并不缺**：`rules/movement.py::resolve_destination` 已经**确定性**地处理"去某地 / 去找某人"（第二路直接拿 `where_is` 的 location 当目的地）。**所以"能不能到"这个问题已经被回答了，只是不靠图。**

🔴 **由此得到一条硬判据**：**不要把地图做成"点一下走过去"的导航器**——那会是**第二份权威**（寻路已经在规则段，且它是确定性的、不该交给 LLM 或前端）。地图要做的是**给人看的空间感**，不是给引擎走的路。

## 4. 🔑 关键发现：`region` 就是现存的"分区"，而且内容包已经在用

2026-09-23 实测 `content/*/scenes.json`：

| 内容包 | 场景数 | `region` 分布 |
|---|---|---|
| **`sgjz`** | 7 | **集市 2 / 下层 2 / 暗渠 2 / 上层 1** ← **天然的**分层结构 |
| **`shenshan`** | 7 | 深山村 5 / 北安县城 1 / 空 1 ← 天然的地理分区 |
| `anmei` | 4 | 秋叶原 1 / 空 3 |
| `qingshi2` | 6 | **全空** |
| `wuxia` | 5 | **全空** |

**为什么这条重要**：

- `sgjz` 那组说明 **`region` 本来就在承担"地图层级"的角色**（上层 / 下层 / 暗渠 / 集市），只是**从来没人把它当地图使过**。`region` 的官方语义（`app/world/models.py:48`）是「消息域：该场景事件归属的地域（跨区域知识边界用）；**空 = 不传播**（2026-09-24 反转）」——**听域用途**，但它同时是一个**天然的空间分区**。
- ⇒ **"按分区分组"的地图形态零新数据、零新字段、零新机制。**

⚠️ **但有一个必须写明的后果**：「转正」表单**不收 `region`**（2026-09-19 决定：守最小需求，场景「听域」输入不加）。所以：

- **玩家新建的场景 `region` 恒为空** ⇒ 分组地图**只对内容包预置场景有效**；
- `qingshi2` / `wuxia` 这种预置全空的包，地图会**退化成一张平铺清单**（仍然可用，只是没有层级）；
- 若要让玩家也能分区，得**先给「转正」表单加 `region` 输入** —— 而那是一条**2026-09-19 明确不加**的决定，需要重新讨论（并注意 `region` 会影响听域语义，见 `MEMORY.md` §8 的场景转正警告）。

## 5. 三个可选形态（**待拍板**）

### 甲 · 分区地图（零新数据）— **建议先议这个**

- **做法**：场景按 `region` 分组（空 region 单列一组），人物挂在场景下（用 `where_is` / `present_at`）。
- 🔑 **它不是新界面**：**＝「位置」面板（`MEMORY-DETAIL` §17B）加一层分组**。位置面板本来就是「抽屉新 tab「位置」」+ 引擎侧 `location_view()`；地图 = 在那个分组上加一层 region 折叠。
- **代价**：region 全空的包退化成平铺清单；玩家新建场景进不了分区（§4 的后果）。
- **数据**：0 个新字段。
- **建议**：**先做位置面板，做出来再看要不要加 region 分组** —— 因为位置面板本身还没做，直接上地图是跳步。

### 乙 · 真连通图（需要边或坐标）

- **做法**：给场景加邻接或坐标，画连线、可选算路径。
- **代价**：撞 `REQ:211` 的退役判据 ⇒ **必须先立"为什么现在需要边"的判据**；且与 `resolve_destination` 的确定性寻路形成**双权威**（得先决定谁说了算）。
- **结论**：**不建议先做**。若真要做，第一步是**写一份"邻接为什么需要回来"的论证**，不是写代码。

### 丙 · 地图 = 一张画（纯视觉示意）

- **做法**：世界层 / 场景层的**附图**（"这一带长什么样"），**不承担任何寻路语义**。
- **代价**：**最低** —— 完全复用 `docs/方案-场景与人物附图-AIWorld.md` 那套：**同一上传口** `POST /sessions/{sid}/assets`（`kind` 增一个 `maps`）+ `assets/` + 玩家显式采纳的心智。
- **优势**：**语义最干净** —— 一张画不产生任何机制后果，"图永远不是真相层"这条底座天然满足。
- **代价的另一面**：它**不回答"有哪些地方、谁在哪"**，只提供氛围。**它不能替代甲。**

**三者不互斥的边界**：丙 是"图"（氛围）· 甲 是"表"（分布 + 分区）· 乙 是"图论"（连通）。**甲 + 丙 可以共存且互补**（一张画 + 一份分区清单）；乙 只有在前两者都做过、且确实缺"连通"才算数。

## 6. 与「位置」家族的关系（🔴 先读，防重复造）

这四件事**共享同一批数据**（`scenes.json` + `where_is` / `present_at` / `region`）：

| 功能 | 回答的问题 | 状态 |
|---|---|---|
| **左栏「在场」/ 顶栏场景卡** | **此刻这一幕**里在哪、谁在 | 场景卡已实现（附图待加） |
| **位置面板**（`§17B`） | **全量**分布：谁在哪、某地有谁 | 未做 |
| **刷新位置**（`§18/§19`） | 让陈旧的位置重新变新 | 未做（影响面已评估） |
| **地图**（本文） | **地方**长什么样 / 怎么分区 | 未设计 |

🔴 **两条不要重复的判据**：

1. **"此刻"已经有人做了** —— 顶栏场景卡（大图 + 在场人物头像行）**就是**"此刻这一幕：哪里 + 谁在"。**地图不必再做一次"此刻"。**
2. **甲 是位置面板的延伸，不是替代** —— 如果先做了地图（甲），位置面板就别再单独做一遍；反之亦然。**开工前先确认没在做已有的那一件。**

## 7. 若选「甲」：落地时会涉及什么（草案级，**拍板后才细化**）

**数据侧**：零新字段。需要一个新的引擎侧视图函数（与 `state_view` 同纪律：**引擎侧生成，前端不自己算**）：

```
location_view() → { region: { scene: [ {name, at, age} ] } }
```

- `age` 用**游戏内时长**表述 —— 🔑 **工具已经存在**：`workorder.py::_rel_seen(clock, at)` 返回 `刚刚 / N 分钟前 / N 小时前 / N 天前`，用的正是游戏内时长。**零成本**。
- ⚠️ 必须同时产出**四个特殊组**（位置面板的既有口径，别漏）：`位置未知` · `已退场` · `临时地点`（`ADHOC_REGION` 哨兵，不在 `scenes.json`）· 主角要**标记**。**任何一组都不能塞进正常分区里**（否则界面在撒谎）。

**界面侧**：抽屉新 tab「位置」→ 按 region 折叠 → 场景 → 人物行（含快照时间）。

**三条纪律（沿用位置面板已定的）**：

- **只读观测**，不做"调度 / 让谁去哪"（会碰"引擎不代笔"）。
- ⚠️ **别用灰显表达陈旧**：项目铁律「灰显只有一种含义 = 编剧这一轮读不到」→ 陈旧用**文字**表达（`_rel_seen`）。
- **人数口径**：位置面板**不含未落卡者**（用户 2026-09-19 拍板），而左栏「在场」**含** ⇒ **两处人数会不一致，这是有意的口径**，必须在文档里写明，否则以后会被当 bug 修。

## 8. 若选「乙」：必须先立什么判据

**在写任何代码之前**，先回答这五个问题（答不上来就说明还不该做）：

1. **为什么现在需要边？** 2026-09-10 为什么退役它？那个理由今天失效了吗？
2. **边由谁维护？** 玩家手填 / 内容包预置 / LLM 推断？—— LLM 推断 = **引擎代笔**（编出不存在的地理），要另立闸门。
3. **与 `resolve_destination` 谁说了算？** 现在寻路是**确定性规则**，地图若也能"到不了"，双权威要收口到一处。
4. **退化怎么处理？** 玩家新建的场景（`region` 空、无坐标）进不了图，界面要明说"未入图"，不能静默丢。
5. **它会不会变成导航器？** 若最终效果是"点一下走过去"，那就**已经越界**（§3 的硬判据）。

## 11. 明确不做（防复活 · 别再提）

1. ❌ **"点一下走过去"的地图导航器** —— 寻路已由 `rules/movement.py::resolve_destination` **确定性**负责，地图再管一次就是**第二份权威**。
2. ❌ **让 LLM 推断地理**（编邻接 / 编坐标）= **引擎代笔**地编世界设定（同"刷新位置"那条：位置推断写进史实已经是最不舒服之处，别再扩大面）。
3. ❌ **地图上做"此刻谁在"** —— 已经有人做了（顶栏场景卡）。**重复造会被两处口径不一致咬。**
4. ❌ **未注册地点直接上图**：解析域虽是"场景表 ∪ 候选册"，但候选册是**运行态、待玩家拍板**的 ⇒ 全量地图若要收它们，得先明确"临时地点"组的呈现（同位置面板的处理），**不能混进正常分区**。
5. ❌ **把地图当真相层**（不许拿图推导位置 / 在场 / 状态 / 关系）。

## 13. 补充答复：两个实现问题（2026-09-23，已核源码）

> 用户提问：① 工作台改了场景（比如加了 `region`），地图会跟着变吗？② 能显示地图当前有谁在吗？
> 两问的答案都是"能"，**但各带一条必须写进界面的限制**；另有一条**场景改名的风险**是这次顺带查出来的。

### 13.1 工作台改场景 → 地图会跟着变吗？**会，立即生效**

**机制**：三个资产保存路径**全都**在 `save_world_assets(...)` 之后**紧跟** `session.reload_world()`：

| 路径 | 位置 |
|---|---|
| `PUT /sessions/{sid}/world`（工作台保存） | `routes_sessions.py:340-341` |
| 场景转正 `POST .../locations/{name}/file` | `routes_sessions.py:513-514` |
| 人物转正 `POST .../unfiled/{name}/file` | `routes_sessions.py:563-564` |

`reload_world()`（`app/runtime/session.py:40-44`）做两件事：`self.world = load_world(...)` **并且** `self.ledger.world = self.world`。后者是关键 —— **账本侧的引用也同步换掉**，否则 `present_at` / `known_set` 还在读旧表。

⇒ **改 `region` 后地图立刻跟着变，不需要重启服务。** 这同时说明**甲形态作为"纯读视图"是成立的**：它只读 `world.scenes`，而 `world.scenes` 永远是刚被刷新的那一份。

⚠️ **但有两件事必须分清**：

- ✅ **改 `region` 是安全的** —— 它只影响**分组显示**。（听域是另一回事：改 `region` 会**追溯**改变历史事件的传播归属，见 `MEMORY.md` §8。）
- 🔴 **改场景 `id`（改名）会切断历史** —— 历史事件的 `location` 存的是**名字符串**；改名后旧名**不在 `scenes.json` 里** ⇒ 那些人**不属于任何注册场景**，于是三重后果：**从所有在场名单里消失**（编剧收不到"在场：X"，他像"人没了"）· 寻路把玩家送到未注册地点 · 事件被 `_event_region` 打上 `ADHOC_REGION` ⇒ **不进任何风闻通道**。
  - **而且现在没有守卫**：`check_world`（`app/world/loader.py:122-124`）对场景**只校验** `start_scene` 在不在表里，**没有改名检查**。对比一下：**主角卡改名有 409 硬锁**（2026-09-21 主角锁定），**场景改名完全放行** —— 这是两条**不对称的纪律**。
  - ⇒ 地图会**如实暴露**这个后果（那些人落进「临时地点」组），但**暴露 ≠ 修复**。落地时**不能**把它放进 `check_world`（`check_assets` 是"临时目录里试写一遍再 `check_world(tmp)`"，那里拿不到事件流）—— **已定要做，落点与判据见 §12 决策记录第 2 条**，**绝不能静默**。

### 13.2 能显示地图当前有谁在吗？**能，但"当前"这个词要拆掉**

**数据完全现成，零新索引**（`app/ledger/queries.py`）：

- `where_is(name)` → `_probe(entity)` = 查 `last_location[entity]` 索引 → 返回**该实体最近一条带 `location` 的事件**（含 `at`）。
- `present_at(scene)` → 域 = `world.npcs ∪ save.unfiled`，跳过 `lifecycle == "retired"`，比对 `event["location"] == scene`。

🔴 **"当前"是错的提法——它是"最后被记录在"，不是"他现在在哪"**：

1. **位置是快照、会陈旧**，而且**没有过期逻辑**（M18 未落地）。
2. 更要紧：**引擎无条件认他在场** —— `present_at` **不校验新鲜度**。所以玩家走到那个场景，编剧会收到"在场：X"，他于是**凭空出现**（`MEMORY-DETAIL` §17C 讲的就是这件事）。
3. ⇒ **界面必须显示快照时间**（`_rel_seen(clock, at)` 现成：`刚刚 / N 分钟前 / N 小时前 / N 天前`，按**游戏内时长**算）。项目铁律：**别用灰显表达陈旧**（灰显只有一个含义 = 编剧这一轮读不到）→ 陈旧用**文字**。

**完整分组（🔴 修正一个提法）**：不是"无 `region` 的全丢进未分区"这么简单 —— **「未分区」与「临时地点」是两个不同的轴**：

| 组 | 判据 | 性质 |
|---|---|---|
| **有分区** | 已注册 且 `region != ""` | 正常 |
| **未分区** | **已注册** 且 `region == ""` | 正常（`region` 空 = **不传播**，2026-09-24 反转；是**合法值**，不是缺省错误） |
| **临时地点** | `location` **不在 `scenes.json`** 里（未注册，`_event_region` 给 `ADHOC_REGION`） | **不是"未分区"的子集**——它压根不是注册场景 |
| **位置未知** | `_probe` 返回 `None`（从未参与过任何带 `location` 的事件） | **开局常态**（除主角外全员如此），**不是 bug** |
| **已退场** | `lifecycle == "retired"` | `present_at` 会跳过它，但 `where_is` 仍返回最后位置 ⇒ **既不进场景组、也不该凭空消失**，附"最后在 X" |
| **主角** | `is_player` | **要标记**，否则会与 NPC 混在一起 |

⚠️ **口径陷阱**：`present_at` 的域**包含** `save.unfiled`（未落卡者），而**位置面板 / 地图已拍板"不含未落卡者"**（2026-09-19）⇒ **地图不能直接拿 `present_at` 的输出**，要自己按 `world.npcs` 过滤。**两处人数会不一致，这是有意的口径**，必须在界面上写明，否则以后会被当 bug 修。
